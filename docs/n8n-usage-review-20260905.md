# n8n 사용 구조 및 최소 운영안 분석

작성일: 2026-09-05 / 월요일 보고용 초안

## 결론

CRM 조회·저장에서 n8n을 분리하고, 외부 서비스 연결 및 저빈도 정기 자동화만 선별 유지하는 과도기안을 권고한다. CRM만 이전했다고 회사 전체 n8n 계정을 해지해서는 안 된다.

## 조사 범위와 한계

- 실제 n8n 워크플로 목록 4개 페이지, 총 153개 항목의 이름·활성 표시를 확인했다. 모든 워크플로 내부 노드나 주기까지 감사한 것은 아니다.
- CRM 쓰기 워크플로의 저장 실행 한 건과 로컬 CRM 소스를 확인했다.
- 청구 관리자 이메일에 접근할 수 없어 실제 요금제·월 사용량·잔여 한도는 미확인이다.
- Overview의 Prod. executions 143 / 실패 3은 집계 기간과 월 과금 지표와의 대응이 확인되지 않아 월 사용량으로 사용하지 않았다.
- 사용자 보고상 한도 초과 상태다. 직접 확인한 CRM 실행 오류는 인증 오류였으며, 그 오류를 한도 초과 증거로 해석하지 않았다.
- 현재 CRM 조회·쓰기 API는 목록에서 Inactive다. 비활성 표시만으로 과거 사용량이나 비활성 원인을 알 수 없다.
- 로컬 소스에는 배포되지 않은 변경이 있다. 로컬 코드의 호출 수를 과거 운영 실행량으로 단정하지 않는다.
- 조사 중 코드·워크플로·활성화 설정·요금제는 변경하지 않았다. 이 문서는 분석 산출물이다.

## 왜 사용량이 커질 수 있는가

1. **자동화 도구가 앱 서버 역할까지 맡았다.** CRM 조회와 저장이 각각 crm-api, crm-write 웹훅을 호출한다. 단순 조회도 상위 워크플로가 실행되면 실행량을 만든다.
2. **20초 주기 동기화가 있다.** crm.html:7295, mobile.html:1134에서 확인했다. 주석상 목적은 PC·모바일 상태를 빠르게 맞추는 것이다. 서버 처리 부담이 작다는 판단과 실행 횟수 비용은 별개다. 숨은 화면·입력·상세보기 중에는 조회를 건너뛰므로 상시 실행으로 계산해서는 안 된다.
3. **사용자 행동과 웹훅 요청이 일대일이 아니다.** 로컬 stage-transition-ui.js:71~74는 단계 변경, Activity, 조건부 Next Action을 별도 요청한다. issue-modal.js:66의 완료도 완료 저장과 Activity 저장으로 나뉜다. 이는 향후 호출량 증폭 구조이며 실제 운영 반영 시점은 별도 확인 대상이다.
4. **여러 부서가 같은 계정을 사용한다.** 견적·CRM뿐 아니라 발주·재고·인사·마케팅·문서·아파트스퀘어가 있다. 각 업무의 실행량은 별도 계측해야 한다.
5. **저빈도 이벤트와 반복 확인을 구분해야 한다.** 제목상 매시간 지연 알림, 매일 리마인드 등이 있다. 실제 주기·시간대·영업일 제한·성공 횟수는 노드와 실행 통계로 확정해야 한다.

모바일에는 인증 전 예열 요청, 창 복귀와 최초 로딩 요청도 있다. 불필요 요청 후보지만 실패한 실행을 곧바로 과금 실행으로 계산하지 않는다. 30초 쓰기 큐 점검도 큐가 비어 있으면 요청을 보내지 않으므로 타이머 횟수를 사용량에 더하지 않는다.

## 실제 목록에서 확인한 업무와 처리 판단

| 분류 | 확인한 워크플로 예 | 권고 |
|---|---|---|
| 화면 조회 | CRM 조회 API (Supabase), 인바운드 상황실 - 구글시트 조회 API, surepoint-history (접수 내역 조회), [슈어] 3. 문의 데이터 불러오기 (load) | 우선 이전 후보. 각 원본 저장소·접근권한을 먼저 확인 |
| 업무 저장 | CRM 쓰기 API (crm-write · 멱등), 견적문의 담당자 배정, surepoint-update (접수 수정) | 인증·권한·감사기록을 유지하며 서버/DB 함수로 이전 |
| 외부 연동 | 견적문의 → 구글시트 + 잔디 + 드라이브, 컨설팅계약서 체결 자동알림, 아파트스퀘어 고객만족도 설문 응답 수집 | 당장은 유지 후보. 업무당 실행 수와 대체 유지비 비교 |
| 주기 알림 | [아스퀘] 주간 방문 배정안 → 잔디 (월 07:30), 견적문의 추적 리마인드 (매일 아침), [슈어] 6. 배정/응대 지연 알림 (1시간마다) | 주간/일간 일괄처리 우선. 시간 단축은 허용 지연시간에 맞춰 결정 |
| 공장·재무 | [발주관리] 3. 이카운트 전표 생성, 넷폼알앤디 월 자재대금 청구서 자동 발송, 용인공장 발주 확인 처리 | CRM 이전과 별도. 대체 검증 전 중단 금지 |
| 정리 검토 | 용인A사 점심주문 수신 (테스트), 임시 - 배정완료 + 응대내용 알림 재발송, My workflow 7, My workflow 3 | Active 표시 확인. 제목만 보고 불필요하다고 단정하거나 삭제하지 않음. 소유자·트리거·최근 실행 확인 |

등록된 워크플로가 153개라는 것 자체는 초과 원인이 아니다. 활성 표시도 실제 실행 횟수를 뜻하지 않는다.

## 계산 가능한 사용량: 가정 시뮬레이션

### 자동조회

가정: 화면 6개가 각각 하루 8시간, 월 22일, 모든 조회 조건을 만족하고 매번 성공한 경우. 저장·초기 로딩·별도 이벤트·다른 업무는 제외한다.

| 조회 주기 | 월 실행 수 |
|---|---:|
| 20초 | 190,080 |
| 2분 | 31,680 |
| 5분 | 12,672 |
| CRM 조회를 n8n 밖으로 이전 | CRM 조회에 의한 n8n 실행 0 |

화면 한 개의 20초 주기는 같은 가정에서 월 31,680회다. 이는 실제 과거 사용량이나 현재 비활성 상태의 예측값이 아니다.

### 최소 유지안

아래는 선택한 기능만 남긴 설계 예시다. 회사 전체 153개 업무를 모두 유지한 예상치가 아니다. 한 업무 이벤트가 하나의 과금 대상 상위 실행으로 완료된다고 가정한다. 30일·주간 실행 4회 기준이다.

| 시나리오 | 계산 | 월 실행 수 |
|---|---|---:|
| 정기 요약만 | 일간 30 + 주간 4 + 월간 1 | 35 |
| 이벤트 연동 + 정기 요약 | 문의 300 + 인계/계약 알림 100 + 설문 50 + 정기 35 | 485 |
| 위 안에 매시간 확인 1개 추가 | 485 + 24 × 30 | 1,205 |
| 완전 이전 | 모든 실행을 다른 구현으로 대체 | 0 |

485회 예시에 계획 여유 20%를 더하면 582회, 1,205회에는 1,446회다. 이 여유는 실패한 실행의 과금 가정이 아니라 이벤트 증가·추가 성공 실행 등에 대비한 예산이다.

실제 최소 사용량 = 유지할 워크플로별 성공 과금 실행 수의 합. 업무당 복수 웹훅, 일정 예외, 호출 방식, 계정 계약 조건을 반영해야 한다.

## n8n을 반드시 써야 하는가

확인한 CRM 처리에는 n8n만 가능한 기능이 발견되지 않았다. 다만 이미 의존하는 타 업무가 있으므로 기술적으로 대체 가능하다는 것과 지금 꺼도 안전하다는 것은 다르다.

| 선택 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 현재 구조 + 요금제 확대 | 전환 작업이 적음 | 반복조회 비용과 한도 의존이 남음 | 임시 복구 수단이지 근본 해결은 아님 |
| CRM 이전 + 외부 자동화 선별 유지 | 반복조회 제거, 기존 운영편의 유지, 이전 위험 분산 | 두 시스템 운영과 경계 관리 필요 | 1순위 |
| n8n 완전 제거 | n8n 실행 한도 및 해당 구독 의존 제거 | 연동·인증·예약·로그·재처리를 직접 운영 | 전체 의존성 대체 및 운영 인력 확보 후 검토 |

## 비용 판단

- 2026-09-05 공식 공개 가격: Starter 연간결제 기준 월 €20 / 2,500회, Pro 연간결제 기준 월 €50 / 10,000회. 사용자 실제 요금제는 미확인이다.
- 사용량이 줄어도 고정 구독료가 비례해서 줄지는 않는다. 전체 계정 기준으로 낮은 요금제가 가능해야 비용 감소가 실현된다.
- Supabase로 옮겨도 DB·저장소·서버 함수·네트워크·외부 문자 비용은 남는다.
- 손익분기 개월 = 초기 이전 비용 / (월 n8n 절감액 - 월 추가 인프라·유지관리비). 분모가 0 이하이면 구독료 절감만으로는 이전을 정당화할 수 없다.
- 조회·저장 중단으로 잃을 수 있는 문의, 누락 복구 시간, 영업 지연 비용도 함께 비교해야 한다.

## 안전한 순서와 성공 기준

1. 사용량 확보 전에도 워크플로별 소유자·업무·트리거·호출 앱 목록부터 확정한다.
2. 조회부터 이전하되 Supabase Auth와 행 단위 권한을 먼저 검증한다. 브라우저에 관리자 비밀키를 넣지 않는다.
3. 단계·배정 등 여러 기록을 함께 바꾸는 저장은 하나의 DB 업무 함수로 처리한다. 중복 요청 방지와 감사기록도 보존한다.
4. 알림은 저장 성공 이후 별도로 재처리 가능하게 설계한다. 외부 문자 발송과 DB 저장은 하나의 DB 트랜잭션으로 되돌릴 수 없다.
5. 이전 전후 결과를 대조하고 중단 기간 누락을 확인한다. 쓰기·발송 양쪽 시스템 동시 실행은 중복을 만들 수 있어 금지한다.
6. 대체 완료한 기존 진입점만 단계적으로 비활성화한다. 원복 절차와 담당자를 문서화한다.

성공 기준 제안:

- CRM 화면 조회·저장이 유발하는 n8n 실행: 이전 완료 후 0회.
- 문의 접수·담당 배정·단계 변경·로그·금액·다음 행동: 서버 저장 후 재조회 일치.
- 대조한 업무 이벤트의 누락·중복: 0건.
- 유지 n8n 월 사용량: 검증된 예상량에 여유를 더하고 실제 계약 한도의 70% 이하로 예산 편성.
- 업무중단 건수·복구시간·월 총운영비를 함께 관찰. 실행 수 감소만으로 성공 판정하지 않음.

## 월요일 보고 문구

> n8n은 견적문의·잔디·구글·공장 등 여러 업무를 연결하기 위해 사용하고 있습니다. 현재는 CRM 화면 조회와 20초 자동갱신까지 n8n이 처리하는 구조가 확인됐습니다. 서버 처리량이 적더라도 호출마다 실행 횟수가 발생하므로, 실제 업무 건수보다 사용량이 크게 늘어날 수 있습니다. 회사 내 다른 자동화도 같은 계정을 사용하고 있어 초과분의 정확한 업무별 비중은 추가 확인이 필요합니다. 단순 증설에 앞서 CRM 조회·저장을 분리하고 외부 자동화만 선별 유지하는 방안을 권고합니다. 기존 접수·청구·발주 업무는 대체 및 누락 검증 후 순차 전환하겠습니다.
