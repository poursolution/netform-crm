# 다음 행동이 보이는 CRM

**다 보여주지 말고, 지금 이어갈 사람과 다음 행동만.**

- 로컬 개선: 담당자 한 명 + 변경, 저장응답 확인, 다음 행동 담당 재검사.
- 배포 전 차단사항: 서버 권한, 계정 간 대기열 격리, 기존 서버의 성공응답 계약.
- 예상 밖의 제약: 기존 수주 1건에서 생기는 여러 추가공사 니즈를 각각 관리해야 한다.
- 성공 기준: 처리시간 감소 + 실제 고객 진전 + 서버 일관성 + 추가 공헌이익. 발송량이 아니다.

## 최종 운영 흐름

아래는 목표 설계다. 녹색의 서버 저장·권한 검증까지 운영에서 확인한 상태를 뜻하지 않는다.

```mermaid
flowchart TD
  A[고객 문의 또는 기존고객의 새 니즈] --> B[지금 필요한 업무 판단]
  B --> C[조직·역할·기존 이력 확인]
  C --> D[추천 담당자 1명 + 다음 행동]
  D --> E{변경이 필요한가?}
  E -->|아니오| F[사람이 확인하고 실행]
  E -->|예| G[이 업무를 맡을 수 있는 사람만 선택]
  G --> F
  F --> H[서버 권한·중복·버전 검사]
  H --> I{저장이 확인됐는가?}
  I -->|미확인| J[완료 표시 금지 · 결과 확인 후 재시도]
  I -->|확인| K[활동과 다음 약속 · 실제 영업 진전]
  K --> L[수주·준공 이력 보존]
  L --> M[고객 관계 유지 · 여러 새 니즈 발굴]
  M --> A
  K --> N[시간·오류·고객 반응·공헌이익 측정]
  N --> B
```

## 한 고객 안의 구조

```mermaid
flowchart LR
  S[현장 1개] --> W[과거 수주 Deal · 변경하지 않음]
  S --> P[장기 관계관리 Pool]
  W --> P
  P --> C1[재도장 니즈 Case]
  P --> C2[주차장 니즈 Case]
  C1 -->|실제 견적발송 확인| D1[새 재도장 Deal]
  C2 -->|실제 견적발송 확인| D2[새 주차장 Deal]
```

현재는 원 수주 Deal별 Pool과 단일 전환 연결이므로 위 다중 Case 구조는 제안이며 미적용이다.
