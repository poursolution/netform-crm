# CRM 일반 read/write에서 n8n 제거하기

작성: 2026-09-05. **전환 설계이며 운영 연결·DB·발송·요금제를 변경하지 않았다.**

## 결론

기존 GitHub Pages 화면과 Supabase DB/Auth/Storage는 유지한다.
n8n의 일반 `crm-api`, `crm-write` 역할을 Supabase 직접 조회/저장과 권한 검증된 DB RPC로
옮긴다. 견적 유입, 외부 기술자문 접수·알림, 실제 문자·카카오 발송·예약·callback은
[승인된 n8n 유지 경계](operational-cutover-20260906/n8n-allowed-boundary.md)로 남긴다.
Edge Function 또는 n8n은 외부 API·비밀키·파일 가공 등 승인된 경계에 한정한다.
데이터베이스를 새로 이사할 필요는 없다. 모든 요청을 Edge로 우회시키지 않는다.
최종 개발 기준은 [아키텍처 결정](architecture-001-supabase-first.md)을 따른다.

```text
기존: PC / 모바일 → n8n crm-api·crm-write → Supabase

전환: PC / 모바일 + Supabase Auth 로그인 세션
          ├─ 직접 조회·독립 저장 → 권한/RLS → 기존 DB
          ├─ 중요한 업무 변경 → 권한 검증 RPC → 기존 DB
          └─ 승인된 외부 작업 → n8n/Edge → 견적 유입·기술자문 알림·문자/카카오 API

     로그인 → 기존 Supabase Auth
     첨부 → 권한 검사 후 Supabase Storage
     예약 → DB 작업목록 + Cron → 서버 발송 작업
     결과 → 서명 검증된 공급자 콜백 → 발송이력
```

## 저장소에서 확인한 사실

- `crm.html` API와 WRITE_API, `mobile.html` CRM_API/WRITE_API는 n8n 웹훅이다.
- 인증은 이미 Supabase Auth를 사용한다.
- `data-cleanup-ui.js`와 `expansion-pool.js`의 일부 조회·기록은 `SB.rpc()`로 직접 연결한다.
  이는 코드 경로 확인이며 해당 RPC의 운영 설치/권한 검증 완료를 뜻하지 않는다.
- SQL에는 `crm_bundle()`을 수정하는 마이그레이션이 있지만 완전한 원본 함수 정의는 없다.
- README는 여러 새 `crm-write` 분기의 운영 연결 필요를 명시한다.
- PC·모바일의 SYNC_MS는 20초다. 숨은 탭·입력/상세 중에는 일부 조회를 건너뛴다.
- 모바일에는 로그인 전 n8n 예열 호출도 있다.
- 실제 n8n 사용량 명세/운영 DB 함수/워크플로 내부는 이번에 조회하지 않았다.

## 역할별 대체

| 업무 | 대체 경로 | 전환 조건 |
| --- | --- | --- |
| 목록·대시보드 조회 | 직접 Query / 안전한 View / 집계 RPC | 페이지 나누기, 필요한 필드, 기존 집계/권한 대조 |
| 배정·담당·계약금액 변경 | 업무별 DB RPC | actor 서버 결정, 대상자 적격, 요청 ID·버전 검사 |
| 활동·Next | 독립 한 건이면 직접 저장, 파생값 동시 변경이면 RPC | 허용 필드·RLS·중복 방지, 유효접촉/기한 이력 유지 |
| 단계전환·확장전환 | 하나의 DB 트랜잭션 | 기존 수주 보존, 실제 견적 발송증명, 부분저장 방지 |
| 사진·자료 | Storage 서명 업로드/다운로드 | 파일·현장 접근권한 검사, 비공개 버킷 |
| 견적 유입·기술자문 외부 알림 | 기존 n8n webhook/automation 유지 | 본문 변경 없이 중복·correlation·CRM read-back 검증 |
| 문자·카카오 | 기존 n8n → 공급자 API 유지 | 공급자 키는 서버 비밀값, 동의·빈도·권한 재검사 |
| 예약·주간보고·휴지통 만료 | Cron + DB 작업목록 | 중복 실행 방지, 실패 재시도 정책, 실행기록 |
| ASQ 동기화 | ASQ → 서명/인증 확인 Edge 또는 주기 조회 | ASQ가 운영정보 정본, 외부 키 브라우저 노출 금지 |

기존 `crm-write` 요청을 이전하는 공용 클라이언트 어댑터는 허용된 `op`만
검증된 직접 저장/RPC/Edge 경로로 고정 매핑한다. 어댑터를 우회한 요청도 DB 권한이
막아야 한다. 새 범용 Edge `crm-write` 서버를 모든 요청의 필수 경유지로 만들지 않는다.

## 지금 장애 중의 안전한 조치

1. 다음 배포에 자동조회·예열·불필요 재시도 중단 스위치를 둔다.
2. 기존 캐시를 쓸 경우 마지막 서버 확인 시간을 표시하고 최신 데이터로 가장하지 않는다.
   계정별 접근 범위가 확인된 캐시만 노출한다.
3. 저장 확인 안 된 작업은 대기/확인필요로 보존한다. 큐·브라우저 데이터 삭제 금지.
4. 예약·캠페인은 자동 재실행하지 않는다. n8n에 이미 접수된 것의 발송 여부부터 대조한다.
5. 장애 중 n8n으로 자동 fallback하지 않는다. 쓰기·발송을 두 경로로 동시에 보내지 않는다.

위 항목은 권장 조치이며 이번 설계 작업에서 실행하지 않았다.

## 이전 순서와 통과 기준

### 1. 현황 보존·서버 계약 확보

- 승인된 Supabase 접근으로 운영 `crm_bundle()`과 관련 RPC 정의/권한을 읽는다.
- 기존 n8n 워크플로 내보내기나 저장된 정의에서 인증·필드변환·외부연결을 확인한다.
  사용량 초과가 워크플로 내보내기도 막는지는 별도 확인한다.
- 반환 JSON 필드, 사용자 권한, write `op` 목록, 실제 사용 분기를 정리한다.
- 대기 중인 write_id와 발송 공급자 요청 ID를 보존한다.
- 비밀키를 채팅·HTML·Git 저장소에 붙이지 않고 서버 Secrets로 등록한다.

### 2. 조회부터 복구

- 안전한 직접 조회/SQL View/집계 RPC를 준비한다.
- 공용 클라이언트 어댑터가 기존 화면의 `deals`, `inquiries` 형태로 맞춰 전달한다.
- 대표/관리자/본사 영업/지사 각각의 조회 범위를 검증한다.
- 임의의 SECURITY DEFINER `crm_bundle()`을 브라우저에 바로 공개하지 않는다.
- DB 원본 집계와 응답의 건수·금액·유효문의·담당자 분류를 대조한다.
- 시험 화면에서 읽기만 새 경로로 연결하고 쓰기는 비활성 상태를 명확히 표시한다.

### 3. 핵심 쓰기 복구

- 배정 → 활동 → 다음 행동 → 금액 → 단계 순으로 지원 목록을 확대한다.
- 기존 큐의 `{write_id, op, payload}`는 어댑터에서 직접 저장/RPC 입력으로 매핑한다.
  새 기능은 목적이 분명한 공용 데이터 모듈을 사용하고 n8n 경로를 추가하지 않는다.
- 응답은 `{ok:true, write_id, operation, entity_version}`이며 신규 생성은 ID를 포함한다.
- 하나의 요청 ID를 서버에 유일하게 저장해 재시도에 같은 결과를 반환한다.
- 서버 저장 후 응답유실 → 명령 결과 조회 → 필요 시 같은 키로 재시도한다.
- 기존 클라이언트 큐는 새 요청으로 일괄 복제하지 않고 완료 여부부터 확인한다.
- 저장 후 새로고침·다른 기기 재조회·무권한 요청·동시수정 충돌을 시험한다.

### 4. 외부 발송·예약·ASQ 이전

- DB 작업목록과 잠금/처리상태를 둔 발송 작업자가 공급자 API를 호출한다.
- 공급자가 중복방지 키를 지원하면 사용한다. 지원하지 않으면 응답불명 작업은
  즉시 재발송하지 않고 공급자 발송이력을 확인한다. DB 큐만으로 외부 발송 1회를 보장하지 못한다.
- 발송 접수·실제 발송·전달 완료·고객 응답은 별개 상태다.
- 기존 예약과 새 예약 작업자 사이에서 업무 소유권을 한쪽에만 둔다.
- 승인된 외부 유입·발송을 제외하고 n8n을 차단한 상태에서 핵심 조회·저장·첨부·확장전환이 동작해야 전환 완료다.

## 호출량과 비용

단순 가정: 6개 활성 세션 × 8시간 × 22일 × 시간당 180회(20초 주기)
= 월 190,080회 조회. 실제는 입력/상세/비활성 시간에 따라 적어진다.
쓰기·포커스 복귀·다른 자동화는 포함하지 않았으며 실제 n8n 과금 명세가 아니다.

- 자동 새로고침은 우선 2~5분 + 저장 직후 재조회 + 수동 새로고침으로 줄인다.
- 2분 주기는 같은 가정에서 월 31,680회로 주기 조회 83.3% 감소다.
- 여러 탭의 요청 합치기, 오류 시 점차 대기, 목록별/변경분 조회를 추가한다.
- Realtime은 권한·메시지 비용·재접속 처리를 검증한 뒤 필요한 목록에만 쓴다.
- Supabase Edge 호출 포함량: Free 월 500,000, Pro/Team 월 2,000,000.
  유료 플랜 초과 호출은 1,000,000회 패키지당 $2이며 패키지 단위 올림이다.
- 최종 설계에서 직접 Query/RPC 조회는 Edge 호출량에 포함하지 않는다.
  위 190,080회를 그대로 Edge 호출량으로 계산하면 안 된다. 실제 외부 처리·콜백·Cron의
  Edge 호출량만 따로 추산한다. Free 한도 초과를 유료 초과요금으로 무조건 이어갈 수 있다는 뜻도 아니다.
- DB 컴퓨팅·트래픽·Storage·Realtime·문자 공급자·기존 플랜 요금은 별도다.
  운영 계정 플랜과 현재 사용량은 확인하지 않았다. 무조건 무료라고 보장하지 않는다.

## 대안 비교

| 방식 | 장점 | 위험/비용 | 판단 |
| --- | --- | --- | --- |
| Supabase 직접 Query + 업무 RPC + 외부만 Edge | 기존 인증·DB 재사용, 불필요한 중간 호출 제거 | 테이블·View·RPC별 권한 정비 필수 | 확정 기준 |
| 모든 요청을 Edge + DB 함수로 처리 | 서버 진입점 일원화 | 단순 조회까지 함수 호출·중간 계층 증가 | 기본안에서 제외 |
| 별도 일반 API 서버 | 실행환경 선택 자유 | 서버 배포·보안·관측·장애대응 추가 | 장기 대안 |

n8n 셀프호스팅은 클라우드 사용량 문제의 다른 대응일 뿐, n8n을 거치지 않는 구조는 아니다.

## 배포 금지 조건

- 기존 상담/배정 SECURITY DEFINER 함수의 실행자 검증이 정비되지 않음.
- 기존 성공 응답을 추측해서 빈 응답을 성공으로 바꿔야만 동작함.
- 조회는 되지만 개인/지사 권한별 데이터 범위가 불일치함.
- 기존 요청의 서버 처리 여부를 모르는데 새 경로로 일괄 재전송하려 함.
- 발송 공급자 자격증명/수신거부/실제 예약 상태 확인이 안 됨.
