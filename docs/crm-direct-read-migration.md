# CRM 조회만 Supabase로 이전

2026-09-05: 로컬 구현 및 모의 테스트 완료. **운영 DB 적용 차단 / 사용자 승인 대기 / 사이트 미배포.**

## 경로

PC/mobile → 공용 crm-read.js → Supabase Auth 세션 → POST /rest/v1/rpc/crm_read_bundle.
쓰기·문자·첨부 준비 등 기존 crm-write 경로와 미완료 요청은 변경하지 않는다.

## 실제 운영 DB에서 확인한 것

- 원본 `crm_bundle()`은 STABLE SECURITY DEFINER, json 반환이며 users/deals/inquiries/brands/leads/dups/generated_at 키를 조립한다.
- 원본 함수는 PUBLIC/anon/authenticated/service_role에 실행권한이 있고 함수 안에 사용자 검사나 담당자별 필터가 없다. 이를 그대로 프론트에 연결하지 않는다.
- users에는 user_id/name/email/role/active/auth_uid가 있고, 사용자 SELECT 정책은 자기 이메일 행 읽기다.
- 역할은 admin/dual/viewer/rep이다. 일부 직원은 Auth 계정 연결이 없다. 이전 작업에서 계정 생성이나 역할 승격은 하지 않는다.
- 운영 CRM 관련 함수는 bundle/contact_move/contact_upsert/opportunity_work_set/site_contacts만 확인했다. 로컬의 새 기능 SQL 전체가 운영에 있다고 가정하지 않는다.

## 승인 요청 범위

1. 기존 프로젝트에 조회 전용 `crm_read_bundle()` 함수 생성.
2. 로그인 UUID가 활성 users.auth_uid와 일치할 때만 반환. 사용자 지정 name/role 파라미터 없음.
3. admin/dual/viewer는 전체조회, rep는 본인 assignee_name 일치 건만. 집계도 본인 기준으로 다시 만들고 전체 중복목록은 반환하지 않음.
4. 원본 `crm_bundle()`의 PUBLIC/anon/authenticated 직접 실행권한 철회. 기존 service_role 실행권한 유지.
5. 테이블·고객 데이터·쓰기 함수·계정·기존 n8n 활성 상태는 변경하지 않음.

운영 DB의 위 권한 변경은 도구 보안 검토에서 명시적 승인 부족으로 실행이 차단됐다.
다른 수단으로 우회 적용하지 않았다. 기존 원본 함수를 anon/authenticated로 직접 호출하는
다른 앱은 영향을 받으므로 사용자 승인과 호출자 확인 후 적용해야 한다.

## 구현 내용

- PC·모바일이 공통 응답 검증·세션 검사·20초 제한·동시 요청 합치기를 사용한다.
- 실패하면 오류를 표시하며 빈 목록 성공, n8n 우회, 예시 데이터로 대체하지 않는다.
- 유효한 빈 배열은 정상으로 처리한다.
- 응답 도착 시 로그아웃/사용자 변경을 확인하고 이전 계정 응답을 폐기한다.
- 20초 주기 전체조회는 2분으로 낮췄다. 기존 편집/숨은 화면 중 조회 방지 유지.
- PC의 이전 공유 캐시는 읽거나 새 고객 데이터로 덮어쓰지 않는다. 미완료 쓰기 큐도 삭제하지 않는다.
- 쓰기 URL을 조회 URL에서 파생하지 않게 분리했다. 조회 성공과 저장 가능 여부를 혼동하지 않는다.

## 배포 전 반드시 수행

- SQL 트랜잭션 적용 후 함수 존재·권한 확인.
- 익명/미등록/비활성 계정은 거절, admin/dual/viewer/rep별 건수·금액 비교.
- 관리자 번들의 기존 keys/deals/inquiries/dups 건수와 원본 비교.
- rep 응답에 타 담당 문의·딜·전체집계·중복 notes가 없는지 확인.
- 실제 로그인한 PC·모바일에서 새로고침, 빈 계정, 만료 세션, 오프라인 테스트.
- 네트워크에서 조회 목적 n8n 호출 0회 확인. 쓰기는 아직 n8n이므로 전체 0회라고 보고하지 않음.
- 로컬 다른 미배포 변경이 많으므로 사용자 변경을 포함한 대규모 일괄 배포를 피하고 배포 범위를 확인.

## 검증 현황

Node 테스트는 HTTP 모의 응답 기반이다. 실제 운영 로그인/DB 권한 검증을 대신하지 않는다.
2026-09-05 1차 실행: 전체 107개 통과(조회 관련 10개 추가).
DB 실제 적용 및 실제 데이터 재조회는 승인 후 진행해야 한다.

## 남은 위험

- 기존 테이블 RLS 경고와 다른 SECURITY DEFINER 함수 권한은 별도 보안 점검 대상이다. 조회 이전만으로 프로젝트 전체 보안 완료를 주장하지 않는다.
- 새 함수는 기존 번들을 서버에서 조립한 뒤 범위를 제한한다. 데이터가 커지면 SQL 단계에서 직접 범위를 제한하고 페이지 단위 조회로 변경해야 한다.
- 미완료 로컬 쓰기/신규 생성 데이터는 기존 동작을 유지한다. 서버 정본 조회와 로컬 미저장 표시는 구분해서 검증한다.
- n8n 쓰기 중단 상태는 이번 조회 이전으로 복구되지 않는다.
