# 남은 업무 1차 — 운영 담당자 대조

기준: 운영 UI `f73e6ca`, Production `ymfbmpnizxvqsamnczow`, 2026-09-13 읽기 전용 조회.
이번 수정은 로컬 후보다. 커밋/push/배포, 운영 DDL/DML, n8n·잔디·구글시트 변경은 하지 않았다.

## P1 / 발견 근거

- 전체 문의 425행. UUID 있는 405행은 연결된 사용자 이름과 전부 일치하며 비활성/누락 사용자 참조도 0건이다.
- UUID 없는 20행: 접수 12, 배정완료 1, 전화응대 완료 1, 종결 6. 이 수치는 DB 행 수이며 화면의 미배정 건수와 같은 의미가 아니다.
- 이름만 있는 3행: 412행 조재연, 98행 서비스운영팀, 238행 중복건(종결). 조재연은 활성 사용자 정확 일치 1명이나 412행 UUID·배정시각·배정이력은 비어 있다.
- 담당자 빈 별도 행과 배정된 행이 공존한다. 예: 서초 병원 별도 행/413행, 현장명 없는 410·411행 주변 별도 행. 전화·브랜드가 같아도 별도 문의일 수 있어 자동 병합 근거로 사용하지 않는다. 364/363행처럼 현장명 표기가 다른 후보도 존재한다.
- 조회 투영은 `i.assigned_to` 및 `coalesce(u.name,i.assignee_name)`를 읽는다. UUID가 있는 행을 서버가 일괄 미배정으로 바꾸고 있다는 근거는 없다.
- 운영 수집 함수의 멱등 래퍼는 이미 존재한다. 레지스트리는 문의 1개/키 1개/반복 키 0개였다. 설치됐다는 사실만으로 모든 외부 수집 경로가 실제 사용한다고 판정할 수 없다.
- 서비스 수집/배정 동기화 RPC는 anon/authenticated 실행 불가, service_role 실행 가능이다. 배정 RPC의 활성 사용자 유일 일치 및 기존 UUID 보존 검사도 확인했다.
- 배정 동기화 RPC 정의에는 assignment_history 추가가 없다. 따라서 이력 0건만으로 과거 배정 시도가 없었다고 단정할 수 없다.

## 화면에서 재현·수정한 별도 문제

`inquiry-assignment-clarity.js`:

1. UUID가 새 담당자를 가리켜도 오래된 이름을 먼저 쓰던 순서를 UUID 사용자 조회 우선으로 수정.
2. 서버가 `assigned_to=null, assignee_name=''`를 명시해도 raw/옛 alias/배정이력으로 담당자가 되살아나던 경로 차단.
3. 일반 보고용 REP_ALIAS의 `서비스운영팀→송보람`을 개인 배정 판단에 사용하지 않도록 차단. 이름 없는 부서는 임의 개인 배정이 아니다. 실제 UUID가 송보람을 가리키면 정상 표시한다.
4. 이름만 저장된 조재연 등 실제 기록과 canonical 필드가 없는 legacy alias 읽기는 유지. DB UUID를 브라우저가 만들어 저장하지 않는다.

세 가지 오류를 먼저 실패하는 테스트로 재현한 뒤 수정했다. 이것이 과거 모든 신고의 단일 원인이라는 주장은 하지 않는다.

## 검증

- 담당자 단위 테스트 13 PASS. UUID/옛 이름 충돌, 명시적 회수, 부서명, 이름만 있는 사용자, raw-only 구형 자료 포함.
- localhost 브라우저: 실제 로딩 순서와 REP_ALIAS에서 위 4개 데이터 형태 검증. 미배정 건수 3→2, 목록 제거, 재조회 서버 정본, 중복 대표행 시나리오 PASS.
- 역할별 브라우저: 관리자 4행/영업사원 2행, 타인 문의·관리자 배정 도구 미노출 PASS.
- 외부 네트워크 차단, 합성 저장 캡처만 사용. 실제 로그인/운영 저장 PASS로 계산하지 않는다.
- 전체 단위 테스트: **614개 중 598 PASS / 0 FAIL / 16 SKIP**. `../remaining-audit-tests-20260913.log`에 기록. 제외 16개는 성공으로 세지 않는다.

## 순서대로 남은 작업 / 범위

1. **운영 데이터 보정 승인 필요:** 412행의 현재값 재확인 후 이름→UUID 보정. 기존 승인에 없는 대상을 임의 변경하지 않는다. 98행 부서는 실제 담당자 확인, 중복 후보는 동일 문의 증거 확인이 먼저다.
2. **외부 수집 도달성 읽기 검증 미완료:** Sheets 최신값과 실제 수집 실행/실패를 대조해야 한다. DB raw는 수신 시점 스냅샷이지 최신 Sheets라는 보장이 없다. 기존 n8n/잔디 경로는 변경하지 않는다.
3. **실계정 저장/RLS/동시 수정 E2E:** 승인된 비업무 테스트 대상과 실제 계정 세션으로 수행해야 한다. 로컬 합성 테스트로 대체 판정하지 않는다.
4. **다른 저장 작업의 ACK/실패 UI:** 활동·다음 행동 등 기존 queue 경로를 순차 검증한다. 관계관리 활동+다음 연락일의 원자적 단일 저장은 서버 계약 확인 후 별도 구현 대상.
5. **공통 UI 정리:** 남은 필터 줄·분석 지표 정의·과거 renderDetail 중복 정리. 저장/권한 검증보다 뒤에 둔다.

재조회용 SQL: `sql/inquiry-assignment-audit-readonly.sql`. 고객 전화번호와 원문 전체를 출력하지 않으며 데이터 변경문이 없다.
