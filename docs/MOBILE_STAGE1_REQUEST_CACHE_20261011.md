# [단계 1] 관리자 요청의 계정·응답 순서 보호

## 한 일

최신 master `0b7852e8824abf3740bb12b10b227ee7e3f84c59`를 읽기 확인하고 모바일 후보를 검사했다. 기존 코드는 요청 캐시를 계정별로 초기화하지 않았고, 조회·담당 확인 응답이 도착한 순서대로 목록을 덮었다. 신규 11개 검사 중 10개에서 수정 전 문제가 재현됐다.

- 계정이 바뀌거나 로그아웃하면 요청 목록·조회 시각·조회 중 상태·기능 사용 불가 상태·담당 확인 캐시를 초기화한다.
- 시작 당시 계정과 로그인 세션 흐름이 유지되는 응답만 반영한다. 같은 계정으로 다시 로그인해도 이전 로그인 중 보낸 응답은 적용하지 않는다. 같은 계정의 프로필 갱신만으로 정상 캐시를 지우지는 않는다.
- 이전 계정의 요청이 남아 있어도 새 계정 조회를 시작할 수 있다. 이전 조회의 종료 처리가 새 조회의 로딩 상태를 끄지 않는다.
- 요청 완료·담당 확인 이후 도착한 오래된 목록, 새 목록 이후 도착한 오래된 담당 확인 응답을 무시한다. 필요한 다음 조회를 위해 캐시 조회 시각을 초기화한다.
- 담당 확인 응답의 성공 여부·요청 ID·대상·받는 사람·종류·회차·기한·상태를 확인한다. 실패하면 다음 클릭에서 다시 확인할 수 있게 한다.

## 바뀐 파일

- `mobile-requests.js`: 계정별 캐시 수명, 조회·회신 응답 순서, 담당 확인 응답 검증.
- `mobile.html`: 해당 스크립트 캐시 버전만 변경.
- `tests/mobile-request-races.test.cjs`: 지연 조회·계정 전환·담당 확인 순서 13개 검사.
- `verify-mobile-request-recovery.cjs`: 실제 모바일 연락 결과 입력으로 완료한 뒤 늦은 조회가 도착하는 경우와 계정 전환 검사 추가.
- 이 문서·검사 결과·진행상태·검증 manifest·후보 패치.

## 추가·바꾼 데이터 필드

없음. 클라이언트 내부의 계정·세션 세대·캐시 변경 순서만 관리한다. 서버 RPC·SQL·권한·완료 조건은 변경하지 않았다. 고객 연락 기록 저장이나 요청 완료를 추가로 자동 실행하지 않는다.
