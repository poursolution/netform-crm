## 2. Claude가 표시 방식을 결정할 항목

새 화면을 요구하는 것이 아니다. 기존 화면을 유지하면서 아래 의미를 어떻게 구분할지 결정해 Codex에게 연결 계약을 넘겨준다.

### 중복 검토·승인함

- 원본 주소와 후보 판정에 사용한 정규화 주소를 비교할 위치. 현재 비교 창에는 원본 주소가 있지만 목록 줄에는 없다.
- Codex가 준비한 후보 데이터: `c.evidence.addresses = [{original, normalized}, {original, normalized}]`. 서울 행정명·공백을 정리하고 번지 하이픈·동·호는 보존한다. 원본 주소를 수정하지 않는다.
- `c.evidence.work`는 `unknown/same/different/not_applicable`, `construction`은 현재 `unverified`, `registrationGapDays`는 접수·등록일 차이다. **공사 기간 차이가 아니다.** 초기 식별 불가 후보에는 evidence가 없을 수 있으므로 null-safe로 읽는다.
- 실제 관계 확인은 공사 범위·요청 목적·실제 공사 시기·기존 상담과의 관련성을 확인한 뒤 한다. 같은 상담 연결 / 같은 현장만 연결 / 별도 공사 유지를 혼동하지 않는다. 기존 상담 연결의 근거 3개·원자 저장 경로를 보존한다.
- 추천 / 사람의 확인 / 실제 적용 완료의 구분, 확인자·시각 표시는 서버의 저장 근거가 있어야 한다. 현재 추천을 ‘처리 완료’로 옮기면 안 된다. 별도 ‘관계만 확정 저장’ API가 있다고 가정하지 않는다.
- 예외 승인 대기 0건은 승인 전후 동작 검증 완료가 아니다. 현재 코드에는 요청자·요청시각·결정자·결정시각·반려사유가 있고, 로컬 테스트로 자기 승인 금지·권한·중복 결정을 확인한다. 운영에 시험 요청을 만들지 않는다.

### 업무·성과·보고

- 전체 대상 = 등록 + 미등록. 미등록 안의 요청 가능 / 이미 요청 중 / 담당 없음 / 제외 사유를 보여줄 위치는 Claude 결정. Codex는 전체 미등록을 요청 가능 수로 축소하지 않는다.
- 계약 정보 ‘오늘 처리’와 ‘전체 누락’의 범위를 구분할 위치. 원자료의 누락 항목별 근거를 사용한다.
- 고객 접촉 준수와 단계 정체는 서로 다른 지표다. 기한·접촉일 미확인은 준수 100%로 계산하지 않는다.
- 기간 발생 실적과 동일 문의 코호트 전환의 구분. 견적 요청 없는 적합 문의를 견적팀 지연으로 평가하지 않는다.
- ‘관리 고객’은 집중/일반/대기/보류/분류 미확인과 실제 0, 조회 실패를 구분. 다음 행동 없는 고객을 ‘여유 있음’ 근거로 삼지 않는다.
- 배정 업무량 임계값 6건·20건은 현재 코드의 잠정값이다. 승인된 운영 설정 키로 연결하려면 별도 설정 계약·SQL·검증이 필요하다. Codex가 값을 임의 확정하지 않는다.
- 약속 누락함, 숫자 근거 보기, 담당 변경 시 미완료 약속 승계는 요청되어 있으나 새 표시 위치를 Codex가 만들지 않는다. 응대 완료가 견적 발송·방문 약속 완료를 뜻하지 않는다.

### 공종 분석·금액

- 현재 진행 예상액 / 계약실적 / 실주 당시 예상액 / 과거 검토 금액의 의미·표시 위치. 기존 계약실적 원장은 체결일·확인된 공사금액·당시 귀속 기준을 유지한다.
- 현재 코드의 공종 막대는 `model.open`, 분류 목록은 `model.rows`다. 목록에 실주가 보인다는 사실만으로 막대가 그 금액을 포함한다고 확정하지 않는다. 선택 기간·ID 목록을 함께 대사한다.
- 공종 0건은 `workItemsOf`의 확정 구조와 기록 원문/AI 응답을 구분해야 한다. 키워드 추정을 확정 분류나 Claude 결과로 표시하지 않는다.
- 현재 단계와 이관 당시 상태를 함께 보여줄 위치. 같은 현장명에서 단계가 다르면 먼저 영업건 ID를 대조한다. 이름만으로 데이터 오류나 중복을 확정하지 않는다.
- 1원 같은 이상값은 검토 대상으로 남긴다. 실제 금액을 추정하거나 원장을 자동 보정하지 않는다. 분석 제외 기준은 별도 승인 필요.
- 같은 공사임을 확인한 후에만 견적 버전으로 연결한다. 다른 공종·연도·계약은 개별 영업건으로 유지한다.

### 경남지사·확장관리

- 지사 실제 연결 / 기록 미확인 / 실담당 미지정은 각각 다른 사실이다. 최초 이관일과 최근 재배정일의 경과일을 구분할 표시 위치는 Claude 결정.
- 확장관리 레코드 수와 고유 현장 수를 분리할 위치. 현장 수는 확정된 현장 ID 기준으로 세고 이름만 같은 건을 합치지 않는다. 현재 ‘건’은 확장관리 레코드 수이며, 계약 원장 건수로 확정하지 않았다.
- 기존 수주금액과 신규 니즈 예상액을 분리할 위치. 현재 확장관리 `wonAmount`는 기존 원본 금액이며 재영업 예상 매출이 아니다.
- 오늘 우선 사후 연락 확인 대상과 이후 니즈 확인·전환 대상을 구분. ‘니즈 0’이 오늘 업무 0을 의미하지 않게 한다.
- 공종 미분류와 기한 경과가 동시에 있으면 두 근거를 보존한다. 대표 분류 한 개 때문에 보완 항목의 실제 수가 사라지지 않게 한다.

### 고객 자산

- 현재 CRM 진행 / 과거 이관 미정리 / 수주 이력 / 관계 분류를 각 행에서도 구분할 위치. 기존 현재 금액과 과거 금액 분리는 유지.
- ‘활성’이 관리 정상이라는 뜻이 되지 않게 한다. 단순 미종결·미분류·미배정과 실제 관계 상태의 차이를 표시할 계약이 필요하다.
- 마지막 고객 접촉과 최근 기록·수정·이관 시각의 차이. 실제 연락일이 없으면 수정 시각을 대신 쓰지 않는다.
- canonical 주소 미입력과 다른 영업·문의에 있는 주소 후보를 구분. 현재 `canonicalAddress`, `addressSuggestion`, `addresses`를 대사한 뒤 전 고객에게 재입력을 요구할지 판단한다.
- ‘과거·휴면’ 묶음과 실제 휴면 상태는 같은 집합이 아니다. 과거/미배정/미분류/휴면의 의미를 구분한다.
- 수주 이력이 있는 현장 필터와 상호 배타적 관계 상태 탭은 별개다. 신규 필터의 위치는 Claude 결정.
- 담당자별 반복 실주는 같은 현장이 여러 담당에게 포함될 수 있다. 전체 고유 현장 수와 담당자 관여 수 합을 구분한다. 주담당 근거 없이 임의 배분하지 않는다.
- 연락처 이름·직책은 원본 필드를 분리한다. 관리소장/동대표를 문자열만으로 일괄 치환하지 않는다.

### 운영 기준

- 정책 확정 여부 / 설정값 저장 여부 / 실제 적용 범위를 별개의 사실로 안내할 방식은 Claude 결정. ‘켜짐’만으로 입력 강제가 구현됐다고 보이지 않게 한다.
- 현재 다음 행동 필수·향후 연도·관리소장 이동·관계 승계 등 일부 설정은 연결되지 않았다. 관련 기능이 전혀 없다고 단정하지 않는다. 예: 담당 변경 이력은 별도 저장 경로가 존재한다.
- 연락 주기(견적 후 7일, 일반 최소 월 1회, 대기 2개월 1회)와 집중/일반 관리 기간·3개월 기산점은 구분한다. 일수↔달력 개월 정책은 사용자 확인 전 변경하지 않는다.
- 연기·예산 미확정은 기회 상실 확인 없이 자동 실주 처리하지 않는다. 원본 사유 기록은 삭제하지 않는다.
- 최초 수신자 우선권은 회의 잠정안, 최초 실제 연결자 자동 귀속은 현재 코드의 정책이다. 두 정책의 승인 근거가 동일하다고 표시하지 않는다. **계약 당시 확정된 sales_owner는 재배정·준공으로 바꾸지 않는다. 인센티브 산식은 계속 보류다.**

## 3. 남은 Codex 검증 (완료로 표시하지 말 것)

1. 배정 임계값 운영 설정 연결: 현재 잠정 6/20과 서버 허용 키·SQL 확인. 정책 값 확정 필요.
2. 고객 자산 886 주소·동일 37일 사례: canonical 조회 응답, ID 연결, 실제 접촉 이벤트와 수정/이관 시각을 읽기 전용 대사. 원본 주소 후보를 자동 확정하지 않음.
3. 공종 분석 93/0·50.7억 사례: 해당 화면의 필터와 영업건 ID별 active/legacy/lost/won, 구조화 공종 여부 대사. 금액 1원의 근거는 사용자/원본 확인.
