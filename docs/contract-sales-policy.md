# 영업운영 CRM 공식 계약실적 기준

정책 ID: `contract-signed-event-v1` · 확정일: 2026-09-20

계약 체결 완료, 계약일, 확정 계약금액, 계약 당시 실적 귀속 담당자가 확인되면 계약일에 영업실적을 인정한다. 공사 착공·준공·현재 단계는 실적 인정 조건이 아니다. 이 지표는 회계 매출 인식과 구분하는 CRM 계약실적이다.

| 사건 | 실적 발생일 | 실적 금액 | 귀속 |
|---|---|---|---|
| 최초 체결 | 계약일 | 최초 확정 계약금액 | 계약 당시 영업담당자 UUID |
| 변경 계약 | 변경 계약일 | 증액 또는 감액분 | 최초 귀속 담당자 유지 |
| 계약 취소 | 취소일 | 남아 있는 계약 잔액의 음수 | 최초 귀속 담당자 유지 |
| 착공·준공·단계 이동·담당자 변경 | 실적 사건 없음 | 0 | 변경 없음 |

조회기간의 신규계약 + 변경증감 + 취소조정 = 순 계약실적. 계약건수는 조회기간에 체결한 계약 건수이며 변경·취소 건수를 신규 계약건수에 더하지 않는다. 화면 표기는 `계약실적`과 `계약 체결일 기준 · 변경·취소는 발생일 반영`으로 한다.

9월 3억 체결, 10월 0.5억 증액, 11월 취소라면 월별 실적은 3억 / 0.5억 / -3.5억이다. 9월의 최초 기록은 유지된다. 취소한 계약을 재체결할 때 기존 취소 이력을 지우거나 되돌리지 않는다. 별도의 검토된 신규 계약 절차가 필요하다.

원장은 최초 날짜·금액·담당자를 고정한다. 이벤트는 순번, 적용일, 증감액, 사유, 기록자, 기록시각을 보존한다. 클라이언트 직접 테이블 변경은 허용하지 않는다. 저장은 버전 검사와 요청 ID 멱등성을 적용하며 취소액은 서버에서 계산한다. 기존 계약 단계의 체결 완료 저장과 원장 기록은 같은 DB 트랜잭션으로 처리한다.

과거 수주 단계, 종료일, 현재 담당자만으로 최초 계약을 자동 생성하지 않는다. 기존 데이터는 계약일과 당시 담당자를 확인하는 별도 검토 후 이관해야 한다. 원장을 읽지 못한 상태는 0원 실적으로 표시하지 않는다.

## 구현 상태

- 공통 계산 모듈: `contract-sales-ledger.js`.
- DB 후보 migration: `supabase/migrations/20260920160000_contract_sales_ledger.sql`.
- 대시보드·성과분석·영업사원 상세·대표 리포트·주간 브리핑의 계약실적은 새 공통 원장과 집계를 사용한다. 기존 `contract-performance.js`는 과거 준공 처리 통계와 운영 흐름을 위해 유지하며 계약실적 계산에 사용하지 않는다.
- 계약 단계 체결 완료 저장은 DB 트리거로 실적 원장과 같은 트랜잭션에 기록한다. 상세창의 계약실적 기록에서 최초 체결·변경·취소를 별도로 기록하고 저장 후 재조회한다.
- 2026-09-20 로컬 검증: 계약 테스트 202개, DB 검증 1개, PC 화면 검사 18개 통과. 운영 DB에는 아직 적용하지 않았다.
- 운영 migration 적용, 과거 데이터 검토 이관, 모든 화면의 새 원장 전환과 운영 검증이 완료되기 전에는 적용 완료로 표시하지 않는다.
