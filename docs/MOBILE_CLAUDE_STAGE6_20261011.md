# [단계 6] 발송 근거(G), 이번에 확인할 것(J-1), 단계 전환 확인(J-2)

상태: 로컬 검토용 부분 구현. 운영 배포·운영 데이터 변경 없음.

## 기준과 바뀐 범위

사용자가 지정한 8766 미리보기의 `guide42-screens.json` 원본 노드와 인라인 스타일을 그대로 사용한다. source43 가이드 20번의 기능 정정(불완전 발송 후보는 참고, 메모 단어로 자동 완료 금지, 기존 업무 보존)을 적용한다. 색·간격·배치·카드를 새로 정하지 않았다.

2026-10-11 기존 로그인 GitHub에서 `poursolution / netform-crm` master의 최신 커밋 `ad20924`(#596)를 확인했다. 로컬 비교 자료의 최신 커밋과 일치한다. PC 견적팀·서버 계산 변경은 이 작업에서 수정하지 않는다.

## 연결한 동작

- C 현장 상세의 기존 `자료 발송 내역` → G, `영업 조건` → J-1. 같은 영업건으로 돌아온다.
- 컨설팅 설계 상세의 기존 `단계 바꾸기` → J-2. 다른 단계의 시안이나 전환 선택 목록을 임의로 만들지 않았다.
- G는 문서·수신자·실제 발송일을 모두 가진 후보만 명시적으로 선택한다. 선택은 현재 계정·영업건에 묶고, 근거가 바뀌거나 다른 계정이 되면 다시 확인한다.
- 실제 이관 메모와 활동에서 읽은 자료는 PC의 `StageTransition.evidence` 후보 추출을 재사용한다. 메모 후보를 이메일 발송 증거로 확정하지 않는다.
- G의 이메일·잔디 두 카드가 있는 검토 주소는 합성 예시다. 실제 이메일·잔디 검색 완료를 뜻하지 않는다.
- J-1은 확인값·유효한 근거 활동 ID·확인일이 함께 있어야 확인 완료로 표시한다. 기존 체크 값이나 메모의 단어만으로 완료 처리하지 않는다.
- J-2는 PC 공통 전환 검증을 사용한다. 실제 견적 버전과 기존 단계 필드를 표시하며 발송일·수신자·D+7 업무를 임의로 채우지 않는다.
- 이전 모바일 목록·상세·단계 변경 창으로 돌아가는 경로는 연결하지 않는다. 승인 원본이나 필수 모듈이 없으면 기존 UI를 대신 노출하지 않는다.

## 실행을 막은 부분과 이유

### G: 다음 단계와 발송 확정

현재 원본은 네 단계 중 첫 `기존 기록` 화면만 있다. 발송일·수신자 확인, 판정, 후속 화면의 실제 원본 노드가 없다. 새 입력 칸이나 화면을 만들지 않았으며 `다음`은 실행하지 않는다.

공통 `message_log`는 문자·카카오의 사용자 확인 기록이며 이메일·잔디 검색 원장이 아니다. 저장 시각을 과거 실제 발송일로 대신 쓰지 않는다. 발송 사건·문서/버전·당시 수신자·실제 발송일시가 함께 보존되는 조회/확정 계약이 필요하다.

### J-1: 공통 질문·근거 계약

기존 `stage_checklist`는 체크 값이고, `stageGuideAutoM`은 메모 단어로 완료를 추정한다. 근거를 연결한 공통 확인 항목 조회 계약으로 볼 수 없다. 운영 모델은 질문을 임의 생성하지 않고 확인 필요 상태를 반환한다. 예시에서는 명시한 근거 활동만 연결한다.

### J-2: 기존 일정 보존

기존 `sql/pipeline-transition/20260906/helper.sql` 73~83행은 발송 단계 전환 시 열린 기존 업무 전체를 취소한 뒤 새 후속 업무를 만든다. 현재 candidate의 일정 보존 SQL은 이 함수를 바꾸지 않았다. `StageTransitionUI.save()` 또한 서버 성공 확인 전에 로컬 단계·활동·업무를 바꾼다.

따라서 둘 다 이 화면의 저장으로 재사용하지 않았다. 전환·후속 업무를 원자적으로 처리하면서 관련 업무 ID를 유지하고 다른 업무를 보존하는 공통 계약이 필요하다. 뒤에서 별도 일정 API를 호출하는 방식으로 이미 취소한 업무를 복구하지 않는다.
