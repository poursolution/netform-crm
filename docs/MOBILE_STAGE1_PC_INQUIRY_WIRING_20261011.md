# 단계 1 — PC 문의 입력의 서버 확인 연결

2026-10-11. **로컬 후보 검증 완료 / 운영 SQL 적용·배포 없음 / 기능 게이트 OFF**.

## 1. 이번에 한 일

PC 견적문의 목록 옆 입력창(`inquiry-v4.js`)과 전체 상세 입력창(`inquiry-detail-v2.js`)의 일반 응대 저장을 같은 `PCInquirySave`로 연결했다. 기존 PC 배치·CSS·입력칸·버튼 이름은 변경하지 않았다. 서버 확인 중인 기존 컨트롤만 잠시 비활성화한다.

저장 순서는 다음과 같다.

1. 계정·문의별 입력, 원래 요청 ID, 진행 상태를 sessionStorage에 먼저 보관.
2. 서버에서 기존 일정 전체를 조회하고 화면의 일정과 대조. 알 수 없는 업무 또는 서로 다른 기존 일정은 연락 기록 저장 전 차단.
3. 응대 기록 저장 및 응답의 문의·기록·요청 ID와 내용 확인.
4. 첫 연결에 해당하면 `crm_inquiry_response_confirm_v1`로 상태·단계 이력 확인. 부재는 이 단계를 실행하지 않음.
5. 응대 근거와 현재 조회의 담당·지문·상태가 맞을 때 기존 일정 유지 또는 새 일정 추가.
6. 전체 확인 후에만 입력 초기화, 다음 문의 이동, 서버 조회 결과 반영.

응답 유실은 같은 요청 ID로 확인한다. 이미 저장된 연락 기록을 다시 만들거나 기존 업무를 완료·취소하지 않는다. 새 경로로 저장을 시작한 건은 게이트를 꺼도 예전 교체 경로로 넘기지 않는다.

실패 후 창을 닫고 다시 열면 같은 입력창에서 보관한 내용을 복원한다. 상대 날짜는 최초 요청의 실제 날짜로 고정한다. 한 탭의 sessionStorage 범위이며 앱 종료 이후 영구 보관 구현이 아니다. 서로 다른 입력창으로 옮겨 새 입력을 작성한 경우, 저장 중이던 내용과 다르면 추가 전송을 차단한다.

## 6. 남은 범위·다음 확인

이전 `MOBILE_STAGE1_PC_INQUIRY_CONTRACT_20261011.md`의 “PC 입력 미연결·HTML 미로드”는 이번 **로컬 후보 연결**로 대체한다. 단계 1 전체 완료는 아니다.

- PC의 문자 발송 후 기록, 방문·견적 등 다른 `InquiryCommand` 경로에는 아직 일정 교체가 남아 있다. 운영 활성화 전에 이어서 정리해야 한다.
- 기존 일정과 다른 내용을 입력한 경우 자동 교체를 막는다. 목록 옆 간단 입력에는 기존 일정 유지/변경을 선택할 승인된 입력 구조가 아직 연결되지 않아, 일부 기존 일정 보유 건은 이 경로에서 저장이 차단될 수 있다. 별도 선택 UI를 임의로 추가하지 않았다.
- 새 첫 응대 RPC는 배정된 문의에 한정한다. 미배정 일반 응대를 새 경로로 저장하는 범위는 미완료다.
- 새 경로의 연락→상태→일정 전체가 하나의 트랜잭션인 것은 아니다. 부분 성공은 보관하고 남은 단계만 재시도한다. 기 저장 응대를 실패로 되돌리지 않는다.
- 실제 서버/계정 비교, 개인 알림 중복 여부, iOS/Android 및 전체 교체 쓰기 경로 검증 후에만 활성화한다.
