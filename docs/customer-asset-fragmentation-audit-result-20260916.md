## 결론

고객자산의 이상 현상은 데이터 삭제가 아니라 연결 단위 분리로 확인됐다.

| 항목 | 건수 |
|---|---:|
| canonical Site | 1,122 |
| Organization | 1,002 |
| 두 개 이상의 연결 조각을 가진 정규화 이름 | 844 |
| 영업 연결 없는 과거 Organization | 30 |
| 해당 Organization의 과거 Note | 37 |

`Site`, `Organization`, `site_id 없는 Deal/Inquiry`를 별도 고객자산 조각으로 취급하는 현재 규칙 때문에 실제 고객의 기록이 여러 묶음으로 보이는 범위가 넓다.

## 연결 밖 데이터

| 상태 | 건수 |
|---|---:|
| `site_id` 없는 Deal | 60 |
| `site_id`와 `organization_id`가 모두 없는 Deal | 60 |

Deal 60건은 `organization_id`도 없으므로 현재 DB 식별자만으로 Site에 귀속할 수 없다. Inquiry 85건도 이름·주소 등 보조 근거를 이용한 확인 Queue가 필요하다.

## 과거 고객 후보 분류

| 후보 상태 | Organization | Note | Contact |
|---|---:|---:|---:|
| 이름 후보 Site 1개 · 사람 확인 필요 | 1 | 1 | 1 |
| 같은 이름의 Site 없음 · 별도 Site 또는 유사명 검색 필요 | 29 | 36 | 11 |
| 이름 후보 Site 복수 | 0 | 0 | 0 |
| 이름·주소 정확 일치 후보 | 0 | 0 | 0 |

현재 정규화 이름의 정확 일치만으로는 30개 중 29개를 기존 Site에 제안할 수 없다. 지역 접두어, `아파트` 접미어, 단지 표기, 주소 일부, 전화번호, 과거 Deal 연결을 함께 사용하는 **후보 검색**이 필요하다. 이 근거는 자동 병합이 아니라 사용자 확인 순위에만 사용해야 한다.

## 대표 이상 패턴

- `황윤선 전체 고객`: 식별자 없는 Deal 33건이 동일한 일반명 아래 33개 조각으로 분리된다. 실제 현장명이 아닌 집계/가져오기 값일 가능성이 높다.
- 동일 정규화 이름 아래 Site 1개와 Organization 1~4개가 함께 존재하는 사례가 다수다.
- 동일 이름의 Inquiry가 `site_id` 없이 개별 조각으로 남은 사례가 있다.
- 이름 자체가 사람명, `무제`, 테스트값, 상품문의 문구인 레코드도 Site 후보에 섞여 있다.

## 다음 구현 순서

1. 영구 연결 저장소를 먼저 정의한다: `legacy entity → site_id`, 확인자, 확인시각, 근거, 상태.
2. 읽기 전용 후보 생성기를 만든다: 정확 ID, 주소 일치, 이름 변형, 연락처, 원본 Opportunity 순으로 점수를 계산한다.
3. 확인 Queue를 `자동확정 가능 / 확인필요 / 별도현장`으로 분리한다.
4. 사람이 확정한 연결만 고객자산, 사람, 확장, 과거 이력의 공통 Site ID로 투영한다.
5. 연결 완료 후 `영업 연결 없는 과거 고객` 별도 섬을 고객자산 내부의 과거자료 상태로 흡수한다.

이 단계에서는 자동 병합, Site 생성, `site_id` 갱신을 수행하지 않는다.
