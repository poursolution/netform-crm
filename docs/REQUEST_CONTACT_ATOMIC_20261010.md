# 요청 응대 저장 1차 — 2026-10-10

## 범위와 반영 상태

기존 `첫 연락 요청` 가운데 문의 대상이고 선택 항목이 `고객 첫 연락` 한 개인 요청 카드의 저장을 수정한다. 디자인·마크업·스타일은 변경하지 않는다. 이 문서는 로컬 구현 결과이며 운영 SQL 적용이나 배포 완료 보고가 아니다.

문의 응대의 비동기 접수 성공을 서버 저장 성공으로 취급해 요청을 먼저 닫던 경로를 교체한다. 응대 기록, 다음 행동, 문의 응대 시각, 요청 상태, 재시도 영수증을 하나의 트랜잭션으로 저장한다. 기존 응대 명령을 호출하고 실제 기록을 검증한 뒤에만 완료한다.

- 연결됨·견적요청·검토중: 요청은 완료, 고객 후속 업무는 열린 상태로 남는다.
- 부재: 시도 기록과 재연락 일정만 저장, 요청은 `working`, 실제 연결 시각은 생성하지 않는다.
- 다음 시도는 같은 요청이 만든 마지막 부재 일정이 그대로 있을 때만 이어서 처리한다. 이전 업무의 원래 기한과 제목을 보존하고 완료시각을 기록한다.
- 별도 방문·견적·회신 일정, 기존 응대 시각 또는 이관 응대 원문이 있으면 저장 전에 상세 확인을 요구한다. 날짜를 대체하거나 약속 주체를 추정하지 않는다.
- 같은 저장 ID 재시도는 원래 영수증만 반환한다. 다른 본문으로 ID 재사용은 거절한다. 재배정 뒤 재시도도 기록을 다시 적용하지 않는다.
- 입력자와 현재 담당자 및 수신 계정이 일치해야 한다. 관리자 대리 입력은 이번 경로에서 허용하지 않는다.
- 보호 대상 요청은 예전 `reply_v1`의 결과 문자열만으로 완료할 수 없다. 로컬 응대 자료를 보고 자동 완료하는 경로에서도 제외한다.

## 바뀐 파일과 서버 데이터

- `work-request.js`: 기존 저장 버튼의 서버 확인·동일 요청 재시도·배포 게이트. 화면 구성은 그대로다.
- `pc-manager-transport.js`, `pc-error-state.js`: `crm_work_request_inquiry_contact_v1` 허용 목록과 오류 이름.
- `sql/20261009211508_request_contact_atomic.sql` 및 동일한 `supabase/migrations/` 파일.
- 새 비공개 표 `crm_security.work_request_contact_receipts`: 실행자·저장 ID·요청 ID·원래 페이로드·서버 ACK·생성시각.
- 기존 `inquiry_contact_logs`의 두 결과 칸, `next_actions`, `inquiries`, `work_requests`를 사용한다. 공개 문의 표에 새 칸은 추가하지 않는다.
- 설치된 `crm_work_request_reply_v1`은 비공개 보존 함수로 보관하고 해당 기본 요청의 완료만 차단한다. 지사·영업건·복합 요청의 기존 경로는 유지한다.

## 검증 및 배포 순서

합성 데이터로 실제 `crm_inquiry_command_v1`을 호출하는 PostgreSQL 테스트를 추가했다. 연결/부재, 기존 계획 충돌, 다음 재시도, 응답 유실 재전송, 권한·재배정·종결·휴지통, 중간 실패 전체 롤백, RLS/실행 권한, 반복 설치를 검증한다. 클라이언트는 서버 확인 전 완료 금지, 잘못된 ACK 거절, 새로고침 후 같은 요청 재시도, 로그인 변경 보호를 검증한다. 기존 요청 카드 브라우저 검사도 새 저장 계약으로 대조한다.

필수 CI → 운영 SQL 적용 및 설치·권한 확인 → 화면 병합·배포 순서다. CRMRelease가 새 RPC 설치를 명시적으로 확인하기 전에는 보호 대상의 빠른 저장을 실행하지 않는다. 운영 고객에게 시험 응대·알림을 생성하지 않는다. SQL은 과거 데이터 일괄 수정이나 n8n 작업을 포함하지 않는다.

## 남은 기능 및 Claude 인계

이번 단계는 모든 요청 유형을 해결하지 않는다. 견적 확인·방문 확인 등 복합 목표와 후속 연락 요청, 영업건 응대 경로의 완료 근거는 별도 서버 계약이 필요하다. 이관 기록 확인이 필요한 기존 문의나 상세에서 별도로 응대한 요청의 자동 정산은 아직 구현하지 않았다. 기존 일정이 변경된 요청은 빠른 저장으로 정리하지 않는다.

Claude는 기존 디자인을 유지하며 다음 단계의 표시를 결정해야 한다. Codex가 임의로 새 UI를 만들지 않는다.

1. 확인과 완료를 분리하는 명시적 확인 동작. 현재 화면 열람 시 `seen`으로 바뀌는 동작은 이번 범위 밖이다.
2. 고객 회신 대기·일정 변경·처리 불가 사유와 요청자 결과 확인. `working`만으로 고객 대기와 미처리가 구분되지는 않는다.
3. 기존 업무 카드와 요청을 한 곳에 연결하는 위치, 기존 약속 충돌 확인 및 예외 사유 입력 위치.
4. 내부 처리 기한·고객 약속·입찰 마감을 구분하는 표시. 이번 SQL은 고객 약속이라고 추정한 새 필드를 만들지 않는다.
5. 복합 요청 목표별 완료 근거, 대리 입력·재배정 책임 이력·정책 버전·대리 승인 기능의 표시 위치와 사용 흐름.

현재 수정만으로 고객 회신 대기 제외, 야간 기한 조정, 기기 간 확인 동기화, 전체 업무 중복 제거, 정책 변경 소급 방지가 완료됐다고 설명하면 안 된다.
