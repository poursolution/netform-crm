# 1단계 — 기존 #550 복합 요청 계약 통합

후속 검증: [일정 보존과 복합 요청 교차 검증](MOBILE_STAGE1_SCHEDULE_OBJECTIVES_CHECK_20261011.md)에서 고객 합의 날짜 변경 보호를 보완했다. 아래 63개 검사는 당시 결과이며, 후속 조합 검사는 75개 통과했다. 운영 설치/배포는 여전히 미실행이다.

## 1. 완료한 작업

Draft #550에 이미 준비된 항목별 조회·판단·후속 업무 저장 계약을 모바일 가이드 작업의 **PC 기능 후보**에 통합했다. 새 계약을 별도로 설계하지 않았다. 이전 보고서의 “계약 연결 미완료” 중 코드 통합과 로컬 검증을 이번에 진행했다. **현재 운영에 배포됐거나 항목별 입력 화면이 완성됐다는 의미는 아니다.**

최신 master 확인: `152d2369e49e2b7d6251f88807651c7f7214213b` (#592). 직전 #591 대비 변경은 `quote-calc.js`, `tests/quote-calc.test.cjs`이며 이번 후보와 겹치지 않는다. #550은 base=master, Draft/open, 미병합 상태다. 사용한 head는 `4386462becd5e8a9e18748ad7ff6ca9f237e8e41`. 공개 PR의 12개 파일을 다운로드해 Git blob SHA로 모두 대조했다.

## 2. 변경 파일

- `work-request.js`: #550의 `WorkRequest.objectives` 조회/저장/후속 업무/재시도 API와 복합 문의 v2 응대 확인을 연결했다. 앞 단계의 영업건/미지원 요청 간편 저장 차단과 일반 활동 시각으로 자동 완료하지 않는 보호는 유지했다. 지원되는 문의 복합 요청은 v2 설치가 확인되면 응대만 저장하고 `working`으로 남긴다.
- `pc-manager-transport.js`, `pc-error-state.js`: 네 함수의 허용 목록·오류 이름을 함께 포함한다. 기존 일정 보존 함수 등록을 유지한다.
- `ops-store.js`: #550대로 PostgreSQL `40001` 충돌을 명시적 롤백으로 전달한다. 결과를 알 수 없는 네트워크 실패는 성공이나 롤백으로 간주하지 않는다.
- `crm.html`: 스크립트 캐시 버전 갱신. 카드/입력/스타일 추가 없음.
- 아래 SQL 두 파일과 각각의 기존 migration 사본: #550 내용을 재작성하지 않고 통합한다.
- `tests/work-request-contact-client.test.cjs`, `tests/work-request-contact-postgres.test.mjs`: #550의 기존 검사를 함께 통합한다.
- `verify-pc-request-proof.cjs`, `run-request-objective-sql.cjs`: 합성 브라우저 및 로컬 DB 실행 확인. 운영 DB를 사용하지 않는다.
- `docs/CLAUDE_REQUEST_OBJECTIVES_HANDOFF_20261010.md`: 기존 계약 전문. 이번 보고서가 통합 상태를 보충한다.

## 3. 서버 데이터와 적용 SQL

| 파일 | 기존 #550 계약 |
| --- | --- |
| `sql/20261009215629_request_compound_contact.sql` | 복합 문의 v2 응대, 항목 조회/판단, 비공개 판단 이벤트·영수증 |
| `sql/20261010090000_request_objective_followup.sql` | 실제 견적·방문 업무 후보, 새 업무/변경 제안, 비공개 후속 업무 출처 이벤트 |

각 파일의 `supabase/migrations/` 사본은 동일 내용이다. 같은 DB에 두 사본을 중복 적용하지 않는다. 이번에 새 migration 이름이나 신규 테이블 구조를 만들지 않았으며 운영 적용은 0건이다.

연결한 RPC는 `crm_work_request_inquiry_contact_v2`, `crm_work_request_objectives_read_v1`, `crm_work_request_objectives_write_v1`, `crm_work_request_objective_followup_v1`이다. v2 응대는 CRMRelease의 명시적 설치 확인이 필요하며, 항목 API는 read/write/followup 세 함수가 모두 확인돼야 켜진다. 모바일 transport 허용 목록은 이번에 확대하지 않았다. 모바일 항목 화면을 연결한 상태가 아니다.

이 결과는 실계정·운영 트리거·동시 세션 전체 검증이 아니다. 일정 보존 신규 SQL 묶음과 #550의 운영 설치 순서/전체 조합 검증도 배포 전 남아 있다. `CRM_SCHEDULE_V1`을 켜지 않았다.

## 5. PC·모바일 차이 및 남은 연결

PC는 `WorkRequest.objectives.read/write/followup` API를 사용할 수 있는 로컬 후보까지 준비했다. 모바일은 앞 단계의 단일 영업건 첫 연락 확인·재시도 상태이며 복합 입력 UI/RPC 연결을 추가하지 않았다. 양쪽 복합 요청 처리의 완전한 일치 검사는 아직 완료되지 않았다.

통화 결과만 저장한 문의 복합 요청은 `working`으로 남는다. 항목 판단을 모두 마치고 명시적 `complete:true`를 저장해야 전체 완료가 될 수 있다. 문의 일반 상세의 기존 응대 저장은 v2 영수증을 자동 생성하지 않는다. 이를 생략하거나 추정해서 항목 저장을 통과시키지 않는다.

## 6. Claude 디자인 인계 — 새 위치를 만들지 않음

기존 `CLAUDE_REQUEST_OBJECTIVES_DISPLAY_DECISION_20261010.md`는 받은 요청 카드의 결과 칩 아래에 추가 확인을 두기로 했다. 이후 #581은 일반 요청의 기본 진입을 현장 상세로 바꾸고, 해당 행이 있는 상단 카드를 숨긴다. 따라서 **기본 화면에서 어느 승인된 입력 위치를 사용할지 Claude 확인이 남아 있다.** 이 통합을 이유로 예전 줄 펼침이나 카드를 복원하지 않았다.

화면 담당은 기존 계약 문서의 네 가지 답(후보 ID, 새 업무 ID, 고객 합의/내부 계획, 충돌 선택)을 그대로 사용한다. 입력을 붙인 뒤 기본 경로로 진입 → v2 응대 → 후보 조회 → 항목 판단 → 전체 완료를 실제 클릭으로 검사해야 한다. 새 배치·버튼·별도 디자인은 Codex가 정하지 않는다.

현재는 1단계 진행 중. 다음 디자인 단계로 넘어가지 않았다. 운영 SQL·GitHub 업로드·병합·배포를 이번 작업에서 실행하지 않았다.
