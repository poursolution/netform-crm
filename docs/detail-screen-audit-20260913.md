## 먼저 고칠 P1

### 1. 문의를 눌렀는데 다른 업무 객체가 열림

근거: `crm.html:4849`의 `linkedDeal()`은 명시적 ID가 없거나 해당 ID를 찾지 못해도 현장명으로 검색한다. 여러 건이면 최근 활동/생성일 기준으로 열린 영업기회를 먼저 고른다. 공종·브랜드·이번 문의와의 실제 연결 여부를 확인하지 않는다.

`crm.html:5346`의 `drwInq()`와 `crm.html:6562`의 `setCurDetail()`은 그 결과가 있으면 문의가 아닌 Deal을 현재 상세 대상으로 설정한다.

재현: 합성 문의 담당자 김성민, 같은 현장명 영업기회 담당자 황윤선, 명시적 연결 ID 없음 → 문의 클릭 후 `CUR_DETAIL.kind=deal`, 담당자 황윤선. 실제 데이터에서 잘못 저장됐다는 증거는 아니지만, 사용자가 문의를 처리한다고 생각하면서 별도 영업기회를 수정할 위험을 확인했다.

수정 방향: 문의 진입은 문의 ID를 유지. 영업기회는 검증된 연결 ID와 별도의 열기 동작으로만 이동. 현장명 일치는 자동 연결이 아니라 확인할 후보로 취급. 기존 연결을 일괄 삭제하거나 실제 데이터를 임의 재배정하지 않는다.

### 2. 금액 UI와 저장 계약이 다르고, 실패 전에 로컬 값을 바꿈

근거: `crm.html:4679`의 `saveBasics()`는 예상·견적·수주 입력값을 로컬 객체에 적용하고 `saveLocal()`을 호출한 뒤 `pushWrite('amount', ...)`를 실행한다.

- 화면에서는 세 금액 모두 수정 가능.
- `operational-adapter.js:30`은 non-null 수주금액을 `AMOUNT_INTENT_NOT_CONNECTED`로 거절.
- 저장소 SQL `sql/reachable-operations-bundle/20260906/staging-apply.sql:1819` 이후는 견적금액이 최신 견적 버전과 같은지 검사하고 예상금액만 갱신한다.
- 합성 테스트에서 수주금액 1,000 입력 → 실제 adapter 거절 → 메모리의 `wonAmt`는 이미 1,000으로 바뀐 상태를 재현. 테스트에서는 실제 저장소 쓰기를 차단했으므로 재접속 후 잔존까지 검증한 것은 아니다.

따라서 첨부 문서의 **“견적 이력을 우회하여 서버에 저장된다”는 결론은 확인되지 않음**. 더 정확한 문제는 **수정 불가 항목을 수정 가능하게 표시하고, 저장 실패 시 화면·서버 값이 달라질 수 있는 구조**다.

수정 방향: 예상금액만 일반 수정. 견적은 버전 등록 경로로 통일하고 수주는 계약/수주 전용 경로로 제한. 검증과 저장 응답 확인 후 반영하거나 실패 시 정확히 복구. 서버 검증은 완화하지 않는다.

### 3. 미전환 문의에 Deal 금액 저장폼이 노출됨

근거: `crm.html:4656`의 공용 상세 렌더러. 브라우저에서 `kind=inq`인 미전환 문의에도 `dv-qamt`, `dv-amt`, `dv-wamt` 세 입력이 존재함을 확인했다. 일반 금액 저장은 `opportunity_id`를 전제로 하므로 문의용 업무와 맞지 않는다.

수정 방향: 문의 상세와 Deal 상세의 노출·저장 대상을 분리. 문의의 기존 담당자/최초응대/다음처리/활동/전환 기능은 유지한다.
