## 결과와 작업 경계

현재 PR의 미래 적용일·기존 업무 처리 선택은 저장 이력이며, 실제 적용을 제어하지 않는다. 아래 두 경로는 PR의 실제 클라이언트 코드와 SQL을 로컬 PGlite에서 실행해 재현했다. 운영 DB·고객 자료·설정은 변경하지 않았다. 현재 운영에서 같은 문제가 발생했다고 확정하는 보고서가 아니다.

Claude가 만든 화면·배치·스타일은 수정하지 않는다. Codex가 기능 계약과 저장 검증을 맡는다. 이 문서는 PR #550의 복합 요청 입력 연결과 별개다. #550은 최신 CI 통과·Draft·운영 SQL 미적용이며 Claude 입력 연결이 남아 있다.

## P1: 미래 적용일과 기존 업무 유지가 실제 계산을 제어하지 않음

- `sql/ops-rules-v2-20261010.sql`은 effective_on / scope / existing_handling을 `crm_rule_history`에만 기록하고, `crm_settings`의 현행 값을 즉시 교체한다.
- `ops-rules.js`의 `save()` → `take()` → `apply()` → `sync()`가 응답 값을 즉시 `CRMRules.get()`과 `OPS_RULES`에 반영한다. 적용일·대상·기존 업무 선택을 검사하지 않는다.
- 재현: 기본 배정 기준 30분 → 10분, 적용일 2099-01-01, existing=keep. 서버 현행값·클라이언트 현행값·OPS_RULES.inquiryAssignMinutes가 모두 즉시 10이 된다. 이력에는 미래 날짜와 keep이 남는다.
- 현재 전역 기준을 다시 읽는 기존 업무 계산도 새 값에 노출된다. 이번 재현은 기준값 경로를 확인한 것이며, 개별 운영 업무의 기한·판정 변화나 원자료 변경까지 확인한 것은 아니다.
- `rules-admin.js`의 keep 설명은 '기존 업무 그대로 · 새 건부터'다. 현재 저장 모델로는 이 선택을 보장하지 못한다. scope도 설명 문자열이므로 대상 ID·선택 조건에 대한 서버 적용 범위가 아니다.

필요한 기능: 현행 기준과 예약 기준을 분리하고, 서버가 KST 적용일과 대상별 정책 버전을 판정해야 한다. 기존 업무 keep은 원래 기준을 유지해야 하며, recalc / ask도 이력 문자열만 저장하고 실행됐다고 취급하면 안 된다. 구현 전 지원되지 않는 적용 명령은 서버와 클라이언트가 명시적으로 거절해야 한다. 화면 선택·문구의 변경 필요 여부는 Claude가 결정한다.

## P1: 구버전 서버가 적용 조건을 버려도 저장 성공으로 처리됨

- PR은 기존 RPC 이름 `crm_ops_rules_v1`을 유지한다. 함수가 존재하는지만 확인하는 available()로는 SQL v1 / v2를 구분하지 못한다.
- `ops-rules.js`의 save()는 apply를 전송하지만, 응답 contract=2 및 요청한 적용 조건의 저장 확인을 요구하지 않는다.
- 재현: SQL v1만 설치한 로컬 DB에 같은 미래 적용 명령을 보냈다. Promise가 성공하고 기준은 즉시 10분으로 바뀌었으며, 이력에 effective_on / existing은 없었다. 클라이언트 meta.contract는 1이다.
- 따라서 SQL 미적용 상태에서 새 화면만 배포하면 선택한 적용 조건이 보존되지 않은 성공 안내가 가능하다.

필요한 기능: 적용 조건을 받는 버전 구분 가능한 서버 계약과 CRMRelease 기능 게이트를 함께 준비한다. 저장 전에 지원 여부를 확인하고 서버도 지원하지 않는 명령을 거절해야 한다. 단순히 응답 후 오류를 띄우는 것으로는 이미 바뀐 설정을 막을 수 없다. 응답에는 저장 명령 ID·정책 버전·현행/예약 구분·적용 조건을 검증 가능한 형태로 반환한다. 실제 저장 성공을 검증하기 전 초안을 지우거나 성공으로 안내하지 않는다.

## 후속: Codex 저장 보호 수정안 준비

수정안은 공유 폴더 `outputs/rule-application-guard-20261010/`에 있다. 원본 재현 자료 `outputs/pr552-functional-review/`는 그대로 보존했다.

- `ops-rules.js`: apply 인자가 있으면 쓰기 RPC 전송 전에 거절한다. 구버전 서버로 적용 조건을 보내 조용히 버리는 경로를 차단한다. 저장 ACK의 ok·rules·요청한 값 일치 여부를 확인하기 전에는 확인된 로컬 기준을 교체하지 않는다.
- `sql/ops-rules-v2-20261010.sql`: 직접 호출에서도 apply 키가 있으면 설정·이력 변경 전에 거절한다. null/빈 객체도 거절한다. 기존 이력 칸과 apply 없는 즉시 값 저장은 유지한다.
- `tests/rule-application-guard.test.cjs`: 실제 v1/v2 SQL과 실제 클라이언트를 연결한 검사 6개 통과. 과거/오늘/미래 날짜와 keep/recalc/ask, 초안 보존, 직접 RPC 거절, 관리자 권한, 불완전 ACK, 통신 실패를 포함한다.

중요한 제한: 예약 적용·대상별 정책 버전·기존 업무 유지가 구현된 것은 아니다. 이 보호안을 사용하면 현재 #552 화면의 적용 조건 포함 저장은 모두 거절된다. 기존 오류 표시 경로가 거절 사유를 표시하고 입력을 보존한다. 입력창 위치·스타일은 바꾸지 않았다. 막힌 선택을 숨기거나 다른 선택으로 바꾸는 UI 판단은 하지 않았다.

원격 #552나 운영에 반영하지 않은 로컬 수정안이다. 원본 #552의 기존 성공 시나리오 검사(미래 적용일을 기록한 뒤 바로 적용됨을 기대하는 검사)는 이 보호안과 계약이 다르므로 그대로 성공 처리하면 안 된다. 통합 시 해당 검사를 차단·초안 보존 검사로 변경하고 화면까지 검증해야 한다. 위 6개 통과를 저장소 전체 CI 통과로 설명하지 않는다.

## 후속: 조회·저장 응답 순서 보호 (2026-10-10)

#552의 최신 457cb4d8 커밋은 stage7-2 검사 문구 수정이다. 예약 적용 엔진 변경은 없었다.

#553에서 추가로 재현한 문제: 저장 전에 시작한 느린 조회가 저장 성공 뒤 도착하면 현행 값과 기준 버전을 과거 값으로 되돌렸다. 두 번째 동시 load()는 첫 조회를 기다리지 않고 기본값으로 완료됐다. 실제 클라이언트의 지연 응답 검사 3개가 수정 전에 실패했다.

ops-rules.js는 저장 시작 전의 조회 응답을 무효화하고, 진행 중 조회를 함께 기다린다. 저장 중 추가 저장은 전송 전에 거절하며, 저장 중 조회는 확정 결과를 기다린다. 실패 후 잠금은 해제되어 재시도할 수 있다. 서버의 다른 관리자 간 충돌 방지나 정책 버전 엔진을 구현한 것은 아니다.

지연 조회·저장 중 조회·중복 저장·실패 후 재시도 등 5개 회귀 검사를 추가하여 관련 검사 25개 통과. 기존 rules-admin 브라우저 검증도 다시 통과했다. 변경된 기능 파일은 ops-rules.js 하나이며 화면 구조·스타일은 그대로다. 적용 조건 포함 저장 차단과 Draft/미배포 상태를 유지한다.
