# 견적문의 상담 연결 API — 원본 두 건 보존

2026-10-06 구현 후보. 아직 운영 DB에 적용하지 않았으며 화면 버튼도 활성화하지 않았다.
디자인 변경, 실제 문의 연결, 배정·상태 변경, n8n 추가는 포함하지 않는다.

## 문제와 결과

옛 `inquiry_activity`는 한 문의를 활성 목록에서 제외한다. 새 API는 두 문의 사이의 관계만 별도 저장한다. 브랜드·전화·원문·담당·상태·최초응대·업무·알림·계약실적을 바꾸지 않는다. 같은 주소는 후보일 뿐이며 관리자가 같은 공사 요청임을 확인한 근거를 입력해야 한다.

## 서버 계약

기존 Auth JWT와 `crm_security.actor()`의 검토된 사용자 권한을 재사용한다. 클라이언트가 전달한 이름·역할은 권한 판단에 사용하지 않는다. 직접 테이블 접근은 차단한다.

| RPC | 인수 | 결과 / 권한 |
| --- | --- | --- |
| `crm_inquiry_consultation_preview_v1` | `p_left`, `p_right` UUID | 관리자 전용. 정렬된 양쪽 ID, 현재 담당/상태, `expected`, 관계 활성 여부 |
| `crm_inquiry_consultation_write_v1` | 양쪽 ID, `p_operation`=`link`/`unlink`, `p_reason`, `p_request_id` UUID, `p_expected` | 관리자 전용. 관계와 감사 사건을 한 트랜잭션에 저장한 뒤 명시적 영수증 반환 |
| `crm_inquiry_consultation_list_v1` | `p_inquiry`, `p_after` UUID 또는 null | 직접 연결된 활성 상대 중 기존 열람 권한이 있는 문의만 최대 20건. `next_cursor` 또는 null |
| `crm_inquiry_consultation_history_v1` | 양쪽 ID, `p_after` 또는 null | 활성 관계 및 양쪽 기존 열람 권한 필요. 원본 사건 기준 최대 20건, 다음 커서 `{at,key}` |

`expected`는 불투명한 변경 버전이다. 미리보기에서 받은 객체 그대로 보내며 직접 재작성하지 않는다. 담당/상태 등 원본 내용 또는 관계 버전이 바뀌면 `STALE_PREVIEW`로 거부한다. 자기 연결, 없는 문의, 휴지통 문의도 거부한다. 입력 순서를 바꿔도 같은 쌍이다.

같은 사용자·요청 ID·정규화된 인수의 재시도는 처음 영수증을 그대로 반환한다. 다른 내용으로 요청 ID를 재사용하면 `REQUEST_ID_REUSE`다. 영수증은 해당 명령의 저장 증거이며 현재 관계 상태가 아니다. 성공/재시도 뒤 목록과 미리보기를 다시 읽는다. 다시 연결하려면 새 미리보기와 새 요청 ID가 필요하다.

두 문의를 UUID 순서로 잠근 뒤 관계를 잠근다. 같은 요청 동시 실행은 사용자/요청별 트랜잭션 잠금으로 직렬화한다. 전체 문의 테이블이나 전체 구글시트를 읽거나 잠그지 않는다. 감사 기록 삽입 실패 시 관계 변경도 롤백한다.

## 이력 범위

- `inquiry_contact_logs`의 실제 CRM 응대
- 적용 성공한 `private.inquiry_change_events`와 해당 문의 `raw.external_change_history`의 출처 ID 있는 외부 변경 기록
- 이번 상담 연결·해제 감사 사건

외부 원본과 raw 복사본은 문의 ID + 원본 사건 ID가 같을 때만 한 번 반환하며 적용 성공한 원본을 우선한다. 출처 ID가 없는 raw 배열 항목은 원본 배열 위치로 구분한다. 같은 문구·전화·날짜만으로 별개 사건을 합치지 않는다. 이 조회 결과를 통화수·응대완료수에 그대로 합산하지 않는다.

반환 필드는 `inquiry_id`, `event_key`, `source`, `source_event_id`, `kind`, `actor_name`, `occurred_at`, `detail`이다. 외부 기록의 상세는 응대내용·상태·종료사유·배정대상만 허용하며 raw 전체나 비밀 설정을 반환하지 않는다. 원본 시각 누락/파싱 실패는 null이다. 현재 시각이나 기록 수신시각으로 고객 응대를 추정하지 않는다.

기존 상세의 문자 발송·견적·업무 요청·ID 없는 옛 자유 메모를 대체하는 전체 이력 API가 아니다. 화면 연결 시 해당 기존 기록을 유지하고 출처 키로 합성한다. 새 API에는 이들 기록을 복제 저장하지 않는다. 해제 후 관련 응대 조회는 차단되지만 별도 감사 테이블의 연결·해제 사건은 남는다.

## 화면 연결 인계 — Claude 위치 확정 필요

기존 비교 화면에는 `연결만`이 있으나 옛 `inquiry_activity` 처리 경로이므로 활성화하지 않는다. 새 API를 쓰는 확인 및 해제 동작의 위치는 Claude가 정한다. Codex는 새 버튼·창·배치·스타일을 만들지 않는다. 프런트 RPC 허용 목록과 화면 호출은 위치 확정 후 연결한다.

저장 흐름: 두 원본 확인 → 새 미리보기 → 같은 공사 요청 근거와 처리 확인 → 새 요청 ID로 저장 → `ok`, ID 쌍, 요청 ID, operation, event_id, version 검증 → 서버 재조회. 네트워크 실패 시 같은 인수/요청 ID로 재시도한다. 일반 `{ok:true}`만으로 완료 처리하지 않는다.

목록은 공용 `list-pager.js`와 쪽 번호를 사용한다. 쪽마다 커서를 보관하고 대상/탭/필터가 바뀌면 1쪽으로 돌아간다. 자동으로 전체 페이지를 불러오거나 아래로 누적하지 않는다.

## 검증과 배포

`node --test tests/inquiry-consultation-links-postgres.test.mjs`

PGlite에서 원본/알림/실적 불변, 관리자·상대 권한, 휴지통/권한 회수, 미리보기 충돌, 역순·재요청, 감사 저장 실패 롤백, 직접 관계만 조회, 이력 중복 제거·20건 커서를 실행 검증한다. 실제 PostgreSQL 다중 세션 동시 실행과 운영 적용은 별도 배포 검증 대상이다.

SQL 후보: `sql/inquiry-consultation-links.sql`. 운영 적용 전 원본/권한 함수 및 이력 테이블 호환을 다시 확인하고 전체 트랜잭션으로 적용한다. 현재 CLI를 사용할 수 없어 임의 timestamp 마이그레이션 파일은 만들지 않았다. 승인된 배포 시 CLI가 생성한 마이그레이션으로 등록한다. 변경은 기존 테이블 UPDATE/DELETE나 신규 트리거/정기 실행을 포함하지 않는다.
