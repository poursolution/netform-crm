# [단계 1 · 문의 저장 검증] 저장 근거와 실패 복구

2026-10-11. 기존 입력 화면의 기능 검증·수정이다. 새 디자인, 운영 배포 또는 단계 1 전체 완료가 아니다.

## 1. 한 일

- `crm_inquiry_command_v1/contact_log`의 `ok:true`만으로 후속 처리를 시작하던 경로를 보완했다. 서버 응답의 문의 ID, 기록 ID, 요청 ID와 실제 저장된 연락 결과·상담 내용·다음 업무·날짜를 요청과 대조한다. 최초 저장과 재전송 응답을 모두 처리한다.
- 서버에 기록은 저장됐지만 응답을 받지 못했거나 근거가 맞지 않으면 같은 요청 번호를 보존한다. 새로고침 후에도 원래 입력으로 재확인한다. 확인 전 단계·일정·완료 처리는 진행하지 않는다.
- 문의 일정의 UTC 시각을 문자열 앞 10자로 잘라 한국 날짜가 하루 빨라지는 문제를 수정했다. 날짜 필드가 있으면 우선 사용하고, 시각만 있으면 한국시간으로 변환한다. 잘못된 날짜는 임의 보정하지 않고 저장 전 확인 대상으로 남긴다.
- 성공 후 입력 상태를 비워 ‘닫기’ 버튼도 막히던 이벤트 분기를 수정했다. 기존 버튼과 배치는 유지했다.

## 2. 바뀐 파일

- `mobile-inquiry.js`: 저장 응답 대조, 날짜 변환, 성공 후 닫기.
- `scripts/verify-mobile-inquiry-browser.cjs`: 기존 CI 브라우저 검사를 실제 대기열·응답 검증을 통과하는 합성 응답으로 갱신. 기존 8개 기능 구역을 유지하고 잘못된 응답·한국시간·닫기 회귀 검사 추가.
- 로컬 `verify-save-recovery.cjs`, `test-result.json`: 실제 새로고침·재진입을 포함한 22개 저장·복구 시나리오.
- 이 보고서와 후보 패치·검증 목록.

## 3. 추가한 서버 필드·적용 SQL

없음. 기존 `sql/inquiry-contact-two-results-20261007.sql`의 응답 규격을 읽고 클라이언트가 확인한다. 이 SQL을 새로 실행하거나 바꾸지 않았다. PC 견적 및 견적 v3 계산·데이터 변경 없음.

## 5. PC와 다른 점·남은 기능

PC와 연락 결과 값·contact_log 필드는 그대로다. 이번 보완은 모바일 문의의 저장 확인이며 PC의 모든 저장 경로가 같은 수준으로 검증됐다는 뜻은 아니다.

문의 `contact_log`는 상담 이력과 flow 상태를 저장한다. 그 뒤의 단계 진행과 `inquiry_next_set`은 별도 명령이다. `inquiry_next_set`의 기존 열린 업무 교체 동작 때문에 다른 기기에서 업무가 추가된 경우의 보존은 아직 보장하지 못한다. 단순 재조회만으로 동시 수정 방지가 완료됐다고 보고하지 않는다.

일반 일정 계약의 현재 `ScheduleFlow`는 영업건 버전과 응대 ACK를 대조한다. 버전이 없는 문의에 이 검사를 생략하고 재사용하지 않는다. 문의 일정의 기대 상태·실제 연결된 업무 ID·명령 재시도 계약을 검증한 후 별도로 연결해야 한다. 견적 v3의 요청·기한 승인 경로는 Claude의 서버 계약을 사용해야 한다.

앱 종료 이후 영구 복원도 미완료다. 현재 복원은 같은 탭의 sessionStorage 기준이다.

## 6. 확인 및 다음 단계

새 화면·배치·스타일 결정을 하지 않았다. 제공 가이드의 다음 디자인 단계로 넘어가지 않았다. 현재 기능 후보와 테스트를 검토할 수 있게 보존했다.

서버 일정 기능 `enabled=false`, 클라이언트 플래그 OFF, 운영 미배포 상태를 유지한다. 최신 모바일 9개 견적 화면 매핑 문서와 Claude의 견적 v3 서버 계약에 대한 기존 요청은 그대로 남아 있다. 포트 8766 디자인 예시는 이번 기능 검증 결과가 아니다.
