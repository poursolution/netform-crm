# [단계 1 · 문의 일정 충돌 보호] 기능 후보 검증

2026-10-11. 사용자 ‘진행해’에 따라 이전 보고의 문의 일정 연결을 이어서 구현했다. 디자인 변경·운영 SQL 적용·배포는 없다. 단계 1 전체 완료가 아니다.

## 1. 한 일

모바일 문의의 새 일정 기능이 켜진 경우에는 기존 `inquiry_next_set` 교체 명령을 보내지 않고 공통 일정 계약을 사용한다. 기존 업무가 있으면 그대로 보존한다. 새 업무가 필요한 경우에도 기존 업무를 취소하지 않는 추가 명령만 사용한다.

저장 순서는 기존대로 **응대 기록 확인 → 첫 접촉이면 단계 진행 확인 → 일정 저장 확인**이다. 시작 전에 문의 담당·상태·전체 업무를 읽고, 문의 화면이 알지 못하는 업무 또는 변경된 상태가 있으면 응대 저장 전 중단한다. 여러 업무를 읽을 때 서버의 20개 페이지를 모두 확인한다.

문의에는 영업건 버전 번호가 없으므로 영업건의 버전 검사를 생략해서 재사용하지 않았다. 문의 전용 연결 모듈이 서버의 `inquiry_guard`를 대조하고 이번 `response_progress`의 검증된 ACK와 현재 상태·응대 시각·수정 시각이 일치할 때만 일정 명령을 준비한다. 업무·담당·그 밖의 문의 필드가 바뀌었으면 일정 쓰기를 멈춘다. 마지막 조회 뒤 발생하는 변경도 서버의 전체 `expected_token`으로 차단한다.

일정 저장 응답이 유실되면 원래 요청 UUID로 영수증을 조회한다. 이미 저장됐으면 새 업무를 만들지 않는다. 기록과 일정이 별도 명령이므로 일부 저장된 경우를 전체 완료로 표시하지 않고 입력·응대 기록·요청 번호를 보존한다.

## 3. 서버 필드·적용할 SQL

기존 테이블의 열 추가 없음. 기존 후보 SQL의 `crm_schedule_list_v1` 응답에 다음 두 필드를 추가했다.

- `inquiry_guard`: 전체 문의 행에서 `status`, `first_response_at`, `responded_at`, `updated_at`만 제외한 값과 **완료·취소 포함 모든 next_actions 행**의 지문. 이 네 칸은 별도의 이번 응대 ACK로 확인한다. 지문은 권한 증명이 아니며 기존 서버 권한 검사를 유지한다.
- `response_state`: 위 네 칸의 현재 값. 문의가 아닌 경우 null.

`crm_schedule_write_v1`는 기존 전체 `expected_token`을 계속 요구한다. 단순히 최신 토큰을 다시 읽어 다른 변경을 승인하는 구조가 아니다.

적용 후보는 `sql/schedule-preserve-v1-20261011.sql`. 세 RPC 이름은 그대로이므로 이미 후보에 포함된 PC·모바일 허용 목록, 오류 이름, CRMRelease 게이트를 사용한다. 새 응답 필드가 없으면 문의 연결 모듈은 저장을 차단한다. **SQL 미적용, 서버 enabled=false, 클라이언트 플래그 OFF 유지.**

확인한 예: 응대 중 다른 기기에서 새 방문 업무 생성 → 일정 쓰기 차단; 기존 23개 업무 보존; 다른 응대의 ACK 사용 차단; 같은 문의의 기존 업무 수정·완료·완료 후 정정도 지문 변경; 일정 저장 응답 유실 후 실제 새로고침 → 추가 생성 없이 저장 확인; 협약완료·해결완료·영업전환·연결된 영업건이 있는 문의에 새 일정 금지.

외부 요청은 차단된 합성 브라우저 검사다. 운영 고객 저장·알림 발송 0건이다. PGlite는 단일 세션이므로 실제 DB의 여러 동시 연결을 검증한 결과가 아니다.

## 5. PC와 다른 점·남은 검증

영업건의 PC·모바일 저장은 기존 공통 경로다. 이번 문의 기능은 모바일 문의에만 후보 연결했다. PC 문의와 견적 요청 등 **모든 기존 교체 쓰기 경로가 전환된 것은 아니다**. 이들이 이후 실행되면 새로 보존한 업무를 취소할 수 있어 운영 기능은 켜지 않는다.

현재 응대·단계·일정은 하나의 트랜잭션이 아니다. 단계 진행 명령 자체의 기존 동시 수정 처리까지 이번 수정으로 원자적으로 바뀌지는 않는다. 이번 보호는 그 변경을 허용한 것으로 간주해 **일정을 덮어쓰는 일을 막는 범위**다. 이미 저장된 응대·단계는 취소하지 않는다. 충돌이 해소되기 전에는 원래 명령을 새 기준으로 자동 재작성하거나 자동 완료하지 않는다.

실 PostgreSQL 다중 연결·원래 쓰기 경로의 잠금 순서·운영 알림/트리거, 실계정·iOS/Android 검증, 앱 종료 이후 영구 복원은 남아 있다. 새 디자인 또는 충돌 해소 UI를 임의로 추가하지 않았다.

견적 v3의 계산·데이터·기한 승인 계약은 Claude 담당이며 이 일정 계약으로 대체하지 않는다. 최신 모바일 견적 화면 매핑과 서버 계약에 대한 앞선 미확인 사항도 그대로다.

## 6. 현재 상태

이전 `MOBILE_STAGE1_INQUIRY_CHECK_20261011.md`에서 ‘모바일 문의의 새 일정 경로 미연결’이라고 한 부분은 이번 **로컬 후보 연결**로 대체한다. 운영 반영 및 모든 교체 경로 연결 완료를 의미하지 않는다. 포트 8766은 승인된 디자인 예시 그대로이며 이번 저장 테스트 화면이 아니다.
