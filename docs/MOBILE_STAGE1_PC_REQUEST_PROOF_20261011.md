# 1단계 — PC 요청의 잘못된 자동 완료 차단

후속 상태: 같은 날 `MOBILE_STAGE1_OBJECTIVES_INTEGRATION_20261011.md`에서 기존 #550 계약을 통합했다. 서버 v2 설치가 확인된 문의 복합 요청의 부분 응대 저장은 그 후속 보고서 기준이며, 미지원 경로 차단과 디자인 보존은 계속 적용한다.

## 1. 이번에 한 일

PC의 예전 관리자 요청 카드가 통화 저장 한 번으로 기존 일정과 복합 요청 전체를 완료하는 경로를 차단했다. **기능의 안전성 보완이며 항목별 완료 기능 구현 완료는 아니다.** 로컬 후보만 변경했고 운영 배포·고객 기록 쓰기·SQL 적용은 하지 않았다.

## 2. 바뀐 파일

- `work-request.js`: 간편 저장은 기존 서버 원자 저장 계약이 있는 문의 단일 첫 연락 요청만 허용한다. 다른 요청은 저장 전에 기존 오류 영역으로 안내하고 선택한 결과를 유지한다. 담당자가 아니거나 이미 닫힌 요청도 사전 차단한다. 문의의 일반 연락 이력 및 영업건의 최근 활동 시각만으로 요청을 자동 완료하지 않는다.
- `crm.html`: 해당 스크립트 캐시 버전만 갱신한다.
- `tests/pc-request-proof.test.cjs`: 복합 요청·후속 요청·부재·담당 변경·종결 상태·기존 견적 판정 보존 검사.
- `verify-pc-request-proof.cjs`: 실제 요청 카드 렌더러/클릭 경로를 합성 데이터로 검사한다. 운영 로그인 화면 검사가 아니다.
- `run-pc-request-regression.cjs`: 기준본의 기존 테스트를 변경하지 않고 후보 코드에 대조한다. 로컬 기준본 폴더가 필요하다.

## 3. 데이터·서버 칸

새 서버 칸·RPC·SQL 없음. `crm_work_request_inquiry_contact_v1`와 `crm_work_request_contact_link_v1`의 기존 단일 문의 계약 및 CRMRelease 확인을 유지했다. 운영 원자료는 변경하지 않았다.

## 4. 확인 결과

| 검사 | 결과 |
| --- | --- |
| 신규 기능 검사 | 10/10 통과 |
| 기존 단일 문의 저장·재시도·응답 순서·견적 조건 검사 | 26/26 통과 |
| 브라우저 합성 검사 | 4/4 통과 |
| 카드 DOM 요소·클래스·동작 속성 비교 | 변경 없음 |

현재 브라우저 검사는 실제 `work-request.js`를 실행하지만 인증·RPC는 합성 자료다. 실계정 서버 저장 및 운영 반영을 입증하지 않는다.

## 5. PC와 모바일의 차이 / 남은 기능

- PC 문의 단일 첫 연락: 기존 서버 원자 계약으로 응대·일정·요청을 확인한다. 부재는 `working`으로 유지한다.
- 모바일 영업건 단일 첫 연락: 앞선 후보의 응대 ACK 및 요청 조회·회신 검증을 사용한다. 조회와 회신 사이 경쟁 조건을 서버가 원자적으로 막는 신규 계약은 아직 없다.
- PC 영업건 첫 연락 및 PC·모바일 복합/후속 요청: 요청 카드에서 일괄 완료하지 않는다. PC의 기존 현장 상세에서 응대 기록 자체는 가능하지만 **그 기록이 복합 요청 항목에 연결되는 기능은 미완료**다. 앞선 모바일의 “PC에서 처리” 안내를 항목별 완료까지 구현됐다는 뜻으로 해석하면 안 된다.
- PC의 예전 `DealDetailV3.record` 외부 호출은 기존 할 일 완료와 새 일정 등록을 수행할 수 있다. 이번 작업은 관리자 요청 카드에서 그 경로를 부르지 않도록 한 것이다. 모든 호출자를 수정했다는 의미는 아니다.
- 견적·계약·낙찰·과거 자료 재개 및 관리자의 명시적 요청 종료 경로는 이번 수정 대상이 아니다. 이들의 별도 증빙 검증이 완료됐다고 주장하지 않는다.

## 6. Claude 인계 / 미결정 표시

색·크기·간격·배치·카드·버튼을 추가하거나 삭제하지 않았다. 기존 완료 안내를 실제 지원 범위에 맞게 바꾸고 이미 있는 오류 영역을 사용했다. 디자인은 제공된 가이드·그림을 따른다.

복합 요청은 기존에 합의한 항목별 입력 위치에 다음 서버 계약을 연결해야 한다. Codex가 별도 위치나 디자인을 만들지 않는다.

1. 요청 당시 항목과 현재 항목의 식별자·버전, 항목별 근거 기록 ID 및 처리 상태.
2. 연결 가능한 기존 견적/방문 업무 ID 후보 조회, 업무 생성 시 반환 ID, 고객 합의/내부 계획 및 충돌 선택 저장 계약.
3. 실제 응대 ACK·현재 담당·요청 회차·목적을 서버에서 함께 검증하는 완료 저장. 동일 operation ID 재시도 및 저장 후 응답 유실 복구.
4. 부재는 고객 연결 완료로 닫지 않는다. 항목 일부 완료로 요청 전체를 닫지 않는다. 기존 방문·견적 일정은 별도 명시적 선택 없이 완료/교체하지 않는다.

해당 계약이 준비되기 전에는 차단을 제거하지 않는다. 현재 1단계는 진행 중이며 다음 디자인 단계로 이동한 상태가 아니다.
