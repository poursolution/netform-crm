# 코칭 일괄 요청 대상·수신자 보존

기준: master a6e087353fe9d9e8dba275c92b5d16c0ef8a0d5f. 디자인 변경 없음.

## 수정 범위

- `rep-window.js`: 담당자 한 사람을 가상 대상으로 보내던 일괄 요청을 실제 문의·영업건 ID별 요청으로 연결한다. 요청함은 같은 주·같은 목적·같은 수신 계정·같은 대상의 서버 저장 확인으로만 판정한다.
- `kpi-b.js`: 사용자 디렉터리의 계정 UUID로 수신자를 확인한다. 선택 대상과 조회 범위를 고정하고 200건씩 저장한다. 미확인 명령과 묶음은 같은 브라우저 저장소에 보존해 창 닫기·새로고침 후 같은 요청 ID로 재시도한다. 나중에 유입된 대상은 원래 묶음에 추가하지 않는다.
- `pc-manager-transport.js`, `pc-error-state.js`: v2 RPC 허용 목록과 오류 이름. `CRMRelease.has` 및 기존 조회 완료 상태가 확인돼야 호출한다. 서버 미설치 시 v1로 우회하지 않는다.

## 서버 계약

설치 SQL: `sql/20261009203001_coaching_target_receipts.sql`.

`public.kpi_actions`에 nullable 필드 6개를 추가한다: `recipient_user_id`, `recipient_name`, `request_id`, `request_group_id`, `request_week`, `batch_index`. 과거 행은 그대로 두며 현재 담당자나 요청 관리자에서 수신자를 역추정하지 않는다.

`crm_security.coaching_request_groups`는 관리자 계정·묶음 ID별 최초 대상, 수신자, 주차, 목적, 판정 버전, 조회 범위의 snapshot을 저장한다. 일반 클라이언트의 테이블 직접 접근은 금지한다. 기존 읽기 함수 `crm_kpi_action_list_v2`는 `k.*`를 반환하므로 새 수신자 필드도 기존 페이지네이션으로 조회된다.

`crm_kpi_request_send_v2`는 기존 admin/branch 권한을 유지한다. 각 배치의 실제 대상 행을 잠그고 `deals.owner_id` 또는 `inquiries.assigned_to`와 담당자 이름을 검증한다. 계정 ID 누락·불일치는 자동 보정하지 않고 저장을 거절한다. 기존 v1 트랜잭션으로 관리자 코멘트·요청 기록·멱등 응답을 함께 저장한 뒤 수신자 메타데이터까지 같은 트랜잭션에서 확정한다.

같은 요청 ID의 응답 유실 재시도는 재배정 후에도 최초 저장 응답을 반환한다. 다른 요청 ID로 같은 묶음 배치를 재저장하려 하면 거절한다. 실패한 배치는 코멘트까지 롤백하며, 앞서 성공한 배치는 유지한다. 최대 5,000건까지 처리하며 초과 시 일부만 보내지 않는다.

## 검증 및 반영 순서

1. 새 PostgreSQL 테스트: 203건 분할, 재배정, 다른 수신자 신규 요청, 응답 유실, 배치 변조, 강제 실패 롤백, 권한 차단, 재적용.
2. 클라이언트 테스트: 새로고침 후 고정 대상 복원, 동일 payload 재시도, 수신자/로그인 변경 및 잘못된 ACK 차단, 서버 설치 게이트.
3. 기존 코칭 CAS·KPI 저장/조회 테스트와 3개 영업사원 브라우저 검사 통과. 레이아웃·크기·색 검사도 기존대로 통과.
4. 필수 CI 통과 후 승인된 운영 DB에 SQL 적용 → 함수/필드/권한 읽기 검증 → PR 병합·Pages 배포 → 쓰기 없는 운영 연결 확인.

운영 SQL·운영 요청 발송은 아직 실행하지 않았다. 새로고침 복구는 같은 브라우저 저장소 기준이며, 다른 기기에서 미완료 묶음을 이어받는 새 화면/조회 기능은 포함하지 않는다.

## Claude 후속 범위

현재 버튼 위치·문구·모양은 유지한다. 부분 실패 원인별 안내, 다른 기기에서 묶음 이어받기, 재배정 때문에 보류된 묶음의 검토·취소 조작은 별도 디자인 결정이 필요하다. 이번 저장 확인은 요청 전달의 증거이며 고객 업무 완료·코칭 성과 달성의 증거가 아니다. 완료 근거·관리자 재확인·코칭 지표 판단은 별도 과제로 남는다.
