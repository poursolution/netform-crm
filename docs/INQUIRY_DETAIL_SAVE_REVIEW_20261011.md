# 문의 상세 저장 회귀 확인 — 2026-10-11

이 기록은 로컬 합성 데이터 검사 결과다. 운영 문의를 저장하거나 운영 서버 설치 상태를 다시 확인한 결과가 아니다. 화면의 노드·배치·스타일은 변경하지 않았으며, 보호된 저장 계약에서 자동 파이프라인 전환을 약속하던 기존 버튼 문구만 `저장`으로 정정했다.

미배정 문의는 현재 공통 일정 계약의 `owner_id`와 `writable` 조건을 충족하지 못하므로 응대 저장을 완료하지 않는다. 예전 `G.inqFlowOff` 스위치가 켜져 있어도 `CRM_SCHEDULE_V1` 보호 경로를 사용하며, 사전검사 실패 시 원문·기존 이력·일정을 보존하고 로컬 응대 완료나 옛 저장 경로를 만들지 않는 것을 실제 상세 버튼으로 확인했다. 이 검사는 미배정 저장 기능이 구현됐다는 의미가 아니다. 담당자를 기존 배정 경로로 지정한 뒤에는 공통 contact → response → schedule ACK가 확인된 경우에만 원문 초기화와 목록 집계 갱신을 허용한다.

합성 RPC의 응대 확인 날짜는 고정 예시 날짜를 제거했다. `sql/inquiry-response-preserve-v1-20261011.sql`은 같은 actor의 실제 `connected` 로그 ID를 검증한 뒤 서버 `clock_timestamp()`를 `first_response_at`, `responded_at`, `updated_at`에 기록한다. fixture도 이 순서를 따른다. 연락 로그의 `occurred_at`은 별도로 보존하며, 과거 로그 시각을 확인 시각으로 복사하지 않는다. 같은 요청 재시도는 기존 확인 시각을 유지하고 변조된 로그 ID는 거절한다.

방문·견적 사실을 저장 중인 저널이 남아 있으면 새 응대 기록을 먼저 만들지 않는다. 방문 예정은 기존 업무·달력 일정이 있을 때 중복 생성 없이 차단하고, 기존 일정 없는 문의는 일정 ACK와 사실 ACK를 각각 확인한다. 응답 유실 후 재진입은 제출 당시 날짜와 요청 번호를 복구한다. 방문 완료 사실 기록은 기존 업무를 자동 완료·취소하거나 파이프라인 영업건을 생성하지 않는다. 전환 자격과 실제 전환은 별개다.

검증 파일: `tests/pc-inquiry-save.test.cjs`, `tests/inquiry-flow.test.cjs`, `tests/pc-inquiry-milestone.test.cjs`, `scripts/verify-inquiry-detail-v2-browser.cjs`. 테스트 RPC는 메모리 안에서만 동작하며 외부 네트워크는 차단한다. 운영 설치·활성화와 화면 배포 확인은 별도 작업이다.

문자·카카오 화면의 명시적 예약은 `pc-inquiry-reminder-save.js`에서 공통 `ScheduleContract`의 `add`와 영수증 조회로 날짜 기준 `기타/internal_plan` 업무 한 건을 추가한다. 기존 고객 약속을 교체하지 않으며, 문자 발송·연락 시도·응대 완료로 기록하지 않는다. `09:00`은 원래 업무 제목에 보존되지만 서버 계약은 날짜 단위이므로 자동 발송이나 정시 알림을 보장하지 않는다고 기존 안내 줄에 표시했다. `pc_reminder` 저널로 본문·절대 날짜·요청 UUID를 보존하고 contact/milestone 저장과 서로 미확인 입력을 덮지 못하게 한다. 신규 단위 검사 12개 및 `verify-inquiry-sms-browser.cjs`에서 실제 버튼의 ACK 대기·응답 유실·재진입·동일 UUID 복구, 고객 기록 불변, 기존 일정 보존을 확인했다. 새 화면·서버 SQL·발송 실행기는 추가하지 않았다.
