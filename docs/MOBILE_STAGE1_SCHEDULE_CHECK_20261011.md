# [단계 1 · 일정 저장 검증] PC·모바일 같은 저장과 실패 복구

2026-10-11. 사용자 ‘진행해’에 따라 최신 견적 서버 계약과 무관하게 진행 가능한 기존 일정 저장 검증을 수행했다. **단계 1 전체 완료나 운영 반영은 아니다.**

## 한 일

실제 PC 상세 입력과 모바일 연락 결과 입력을 브라우저에서 조작했다. 저장 RPC만 합성 서버로 바꾸고 공통 입력 계획·전송 계약·저장 순서·응답 검증은 후보 코드를 그대로 실행했다. 운영 요청 0건.

검사에서 PC 창 재진입 시 복원된 메모가 빈 textarea 값으로 덮이는 오류를 발견해 수정했다. 저장 전 검증에서 차단돼 아무 명령도 보내지 않은 경우에는 입력 변경을 막던 잠금을 해제한다. 이미 전송한 명령이 있으면 원래 입력·요청 UUID를 보존한다.

고객 합의 일정은 일반 내부 일정 변경으로 바꾸지 않도록 클라이언트와 SQL에서 막았다. 기존 고객 합의 이력이나 명시적인 ‘고객 약속’ 표식을 확인한다. 합의 여부가 없는 값을 고객 합의로 추정하지 않는다. 향후 재합의 근거 연결 경로가 제공될 때 별도로 연결해야 한다.

## 바뀐 파일

- `deal-detail-v3.js`: PC 연락 결과 재진입 시 복원 메모 유지, 저장 전 차단 후 입력 수정 허용. 배치·스타일 변경 없음.
- `mobile-entry.js`: 서버 명령을 보내기 전 차단된 저장 시도의 입력 잠금 해제. 전송 후 실패는 같은 요청 ID 유지.
- `schedule-flow.js`: 고객 합의 일정 변경 전 차단.
- `sql/schedule-preserve-v1-20261011.sql`: 고객 합의 일정의 일반 변경을 서버에서도 거절.
- `tests/schedule-contract.test.cjs`, `tests/schedule-flow.test.cjs`: 원래 일정 불변·고객 합의 보호 검사 추가.
- `tests/schedule-browser-fixture.cjs`, `build-gated-browser.cjs`, `verify-schedule-gated-browser.cjs`: 실제 PC/mobile 입력 경로의 비교·응답 유실·재진입 검사.
- `schedule-gated-browser-result.json`, `schedule-sql-result.json`, `verification-manifest.json`, 패치·상태 문서: 검사 결과와 적용 후보 기록.

## 추가·바꾼 데이터 필드

이번 보완에서 추가한 필드 없음. 기존 일정 계약 후보의 `date_basis`와 이벤트 이력을 사용한다. **운영 SQL 적용 및 데이터 변경 없음.**

## PC와 다른 점

이번 9개 시나리오에서 서버로 보낸 응대·일정 명령은 PC·모바일이 같았다. 이는 전체 CRM 동작의 일치를 증명하지 않는다. 견적 예정일의 모바일 3일 고정과 견적 v3 계약 미연결은 이전 0단계 보고의 미완료 항목으로 남아 있다.

## 질문 / 다음 작업 조건

새 디자인 결정 없음. 최신 모바일 전체 묶음과 Claude의 견적 v3 서버 계약은 여전히 필요하다. 이 일반 일정 계약을 견적팀 기한 승인이나 견적 계산 계약으로 대신 사용하지 않는다.

서버 `enabled=false`, 클라이언트 플래그 OFF 유지. 문의·견적 요청의 기존 교체 경로, 실제 DB 동시성·알림 트리거 통합 검사까지 끝나기 전에는 운영에서 켜면 안 된다. 포트 8766은 사용자 제공 디자인 예시이며 이번 기능 검증 화면이 아니다.
