# [단계 1] 모바일 요청 처리의 잘못된 완료·실패 복구 보완

2026-10-11. **로컬 후보 검증 완료. 운영 배포·실계정 쓰기 없음.**

## 한 일

모바일에서 응대는 저장됐지만 관리자 요청 처리에 실패한 경우, 입력과 저장 진행 상황을 남기도록 수정했다. 다시 열어 저장하면 기존 응대 기록을 재사용하고 남은 요청 처리를 확인한다.

기존 코드는 요청 처리 실패를 `failed`로 바꾼 뒤 저장 복구 정보를 삭제했다. 서버 응답도 요청 ID만 같으면 성공으로 처리했다. 현재 후보는 대상 영업건·받는 사람·요청 항목·실제 상태·연결 결과·다음 업무를 확인한 뒤에만 마무리한다.

부재·번호 오류는 `action: done, absent: true` 대신 기존 `action: working`을 사용한다. 저장소의 기존 `work-request-v1-20261005.sql`은 전자를 `absent`라는 닫힌 상태로 처리하고, 후자는 `working`이라는 열린 상태로 처리한다. 화면 안내와 실제 요청 상태가 다르던 경로를 수정했다. 기존 상태값을 재사용하며 모바일 전용 상태는 만들지 않는다.

## 추가·변경한 데이터 필드

서버 필드·SQL·RPC 추가 없음. 기존 서버 함수를 사용한다.

- `crm_work_request_list_v1`: 해당 영업건 요청의 현재 상태 확인.
- `crm_work_request_reply_v1`: 실제 연결은 `done`, 부재·번호 오류는 `working`.
- 기존 계정별 sessionStorage 저장 복구 항목에 `requestSnapshot`, `requestResults`, `infoHandled`, `infoError`를 보관한다. 서버 표가 아니며 새 인증정보를 저장하지 않는다.

같은 연락 기록은 기존 큐의 요청 ID로 재사용한다. 요청 회신에는 서버 저장 영수증이 없으므로 재시도 전 현재 요청 상태를 대조한다. 직전 저장과 정확히 맞는 완료 상태 또는 요청한 `working` 상태가 확인되면 추가 쓰기를 하지 않는다. 이는 동일 트랜잭션·요청 이벤트 영수증을 구현했다는 뜻이 아니다.

## PC와 다른 점 / 남은 계약

- 완료 가능한 요청을 **영업건의 단일 `고객 첫 연락` 요청**으로 제한했다. 첫 연락+견적/방문 확인처럼 여러 항목이 있는 요청과 후속 연락의 수신·반응 확인은 통화 한 건만으로 완료를 증명할 수 없다. 기존 비활성화 안내를 사용해 PC 처리로 돌린다. 새 화면을 추가하지 않았다.
- PC 전체 요청 처리와 상태 일치 검증은 아직 완료하지 않았다. PC의 동일 위험 경로와 서버의 응대 근거 결합 계약을 추가 대조해야 한다. 문의 대상 요청의 전용 원자 저장 계약은 이번 영업건 처리에 대신 사용하지 않았다.
- 기존 회신 RPC에는 예상 버전·응대 기록 ID를 서버에서 원자적으로 확인하는 인자가 없다. 재조회와 응답 검증은 잘못된 표시를 줄이지만 조회와 쓰기 사이의 모든 경쟁 변경을 막는 서버 계약은 아니다. 전체 일정 보존 모드는 계속 OFF이며 운영 활성화 조건은 아직 충족되지 않았다.
- 공사 시기 저장 실패는 이전 동작처럼 별도 실패로 보고한다. 요청 재시도 때 이미 처리한 공사 시기 저장을 반복하지 않으며, 그 실패 사유도 유지한다. 공사 시기 저장 자체의 응답 유실·재시도 계약 완성은 별도 과제다.
- 방문·견적 일정 보존 계약은 이전 `MOBILE_STAGE1_MESSAGE_SAFETY_20261011.md`의 미완료 항목을 유지한다.
