# Claude → Codex 인수인계 — 응대 결과 정정 (after_deploy 17)

작성: 2026-10-10 · Claude Code (디자인 · 화면 담당)
근거: 대표 전달 묶음 `design_handoff_after_deploy` 17번, 시안 `그 자리에서 보완 · 후속 연결 시안.dc.html` 5번 칸.

이 문서는 요청입니다. 서버 함수 · 완료 판정 · 저장 계약은 Codex 담당이라 Claude 는 화면을 만들지 않고 멈췄습니다. 아래 "정해지지 않은 것"은 임의로 정하지 않았습니다.

## 1. 대표가 원하는 것 (시안 그대로)

- 잘못 넣은 응대 결과를 고친다. 예: `통화 연결` → `부재` (10.8 이필선 기록).
- 저장 전에 **영향 미리보기**: 최초 응대 시각 해제 · 관리자 요청 '완료' → '회신 대기' · 첫 연락 KPI 1건 빠짐.
- 저장하면 관련 요청 · 단계 · 집계를 **다시 계산**.
- **이력 보존**: 정정자 · 시각 · 사유 · 원래 값. 원래 기록을 지우거나 덮어쓰지 않는다.

## 2. 왜 화면만 먼저 만들지 않았나

- 응대 기록을 고치는 서버 길이 없습니다. 지금 있는 것은 새 기록 추가(`activity`) · 다음 할 일(`next_action`) · 단계 정보(`crm_deal_stage_fields_update_v1`)뿐입니다.
- 화면에서만 표식 메모로 덮으면 화면 판정(ContactState · isMeaningfulContact)과 서버 값(`last_meaningful_contact_at` · 최초 응대 시각 · 요청 완료 판정 · KPI 스냅샷)이 서로 달라집니다. "같은 정보 같은 판단" 기준에 어긋납니다.
- 상세 창의 응대 이력 줄(`deal-detail-v2.js` 의 `.idv-msg`)에는 기록 번호가 실려 있지 않습니다. 정정 대상을 가리키려면 줄에 `activity id` 를 실어야 합니다(이 부분은 Claude 가 화면 작업 때 함께 넣습니다).

## 3. 서버에 필요한 것 (제안 — 이름 · 모양은 Codex 가 정함)

| 항목 | 내용 |
|---|---|
| 정정 명령 | 대상 기록 번호 · 새 결과(연결됨 · 부재 · 검토중 · 자료요청 · 견적요청 · 회신대기 · 방문희망 · 다음 할 일 없음) · 사유(필수) |
| 보존 | 원래 종류 · 원래 글 · 원래 결과 · 정정자 · 정정 시각 · 사유. 원래 기록은 지우지 않음 |
| 권한 | 기록한 본인 · 그 영업건 담당 · 관리자 (미확정 — 아래 4번) |
| 미리보기 응답 | 저장 없이 영향만 돌려주는 호출(또는 `dry_run`). 최초 응대 시각 변화 · 영향받는 요청 번호와 상태 변화 · 단계 영향 · KPI 항목별 증감 |
| 다시 계산 | `last_meaningful_contact_at` · 최초 연결 시각 · 요청 완료 판정(완료 → 회신 대기 등) · 첫 연락 / 연결 KPI |
| 화면 응답 | 정정 뒤 기록(정정 표시 포함) · 바뀐 요청 목록 · 영업건 버전 |

## 4. 정해지지 않은 것 (대표 결정 필요 — Claude 는 정하지 않음)

1. 누가 정정할 수 있나: 기록한 본인만 / 담당 · 팀장까지 / 관리자만.
2. 며칠 전 기록까지 정정할 수 있나(예: 주간 KPI 저장 뒤의 정정은 저장된 주간 결과를 바꾸나, 다음 주에만 반영하나).
3. 정정으로 요청이 '완료'에서 되돌아갈 때 요청자에게 알림을 보내나.
4. 연결 → 부재 처럼 줄이는 정정만 허용하나, 부재 → 연결 처럼 늘리는 정정도 허용하나(늘리는 쪽은 근거를 더 받나).

## 5. Claude 가 붙일 화면 (서버 함수가 생기면)

- 응대 이력 줄의 [정정] → 그 줄 아래 한 칸: `원래 값 → 새 값` · 사유 · 영향 미리보기(서버 응답 그대로) · [정정 저장].
- 정정된 줄: 원래 값에 취소선 + `정정 · 정정자 · 시각 · 사유`.
- `CRMRelease.has('<함수 이름>')` 이 참일 때만 [정정] 을 보인다. 없으면 버튼 자체가 없다.
- 미리보기 숫자는 화면에서 다시 계산하지 않는다(서버 응답만 표시).

## 6. 참고 — 이번에 같이 바뀐 화면 쪽 사실 (after_deploy 13 ~ 16 · Claude 구현)

- 단계 정보에 새로 쓰는 칸(기존 `crm_deal_stage_fields_update_v1` 그대로 · 새 SQL 없음): `sent_basis` · `sent_date_check` / `schedule_basis` · `schedule_check` / `contract_basis` · `contract_check`. `*_check = '확인 불가'` 는 날짜 없이 남기는 표시이고 판정은 계속 '판정 불가'입니다.
- 경쟁 · 입찰 목록의 기준 날짜가 판정 함수와 같아졌습니다: 입찰 마감 → 결정 일정 → 현설 → PT · 협의(`pipeline-workspace.js`). 전에는 결정 일정 · 현설만 있는 건이 목록에서 '일정 미등록'으로 보였습니다.
- 응대 결과에 `견적요청` 이 추가됐습니다(기록 글머리 `통화 완료 · 견적 요청`). 다음 업무는 `견적 요청 등록(잔디) · 물량 산출 n일 목표`(n = 운영 기준의 견적 처리 일수).
- 같은 영업건에 열린 연락 요청(종류 first · follow)이 있으면 응대 기록의 전화 업무 기한을 그 요청 기한에 맞추고 글 끝에 `· 요청 <요청자>` 를 붙입니다. 요청 자체의 완료 연결(F1)은 건드리지 않았습니다.
