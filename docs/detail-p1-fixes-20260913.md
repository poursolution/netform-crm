# 상세화면 P1 수정 결과

상태: 로컬 수정·검증 완료. 커밋/운영 배포/Production DB 적용 없음.
앞선 `detail-screen-audit-20260913.md`는 수정 전 조사 기록이다.

## 변경

1. **문의와 영업기회 식별 분리**
   - 문의를 눌러도 `CUR_DETAIL.kind=inq`를 유지한다.
   - 동일 현장명만으로 영업기회를 자동 선택하지 않는다.
   - 명시적 연결 ID 또는 유일한 역방향 문의 ID 연결만 인정한다.
   - 연결 ID 누락 대상, 복수 연결, 정방향·역방향 불일치는 선택하지 않는다.
   - 이미 연결 표시가 있으나 대상을 확인할 수 없으면 새 영업기회 중복 생성도 차단한다.
   - 실제 연결된 영업기회는 별도 버튼으로 연다. 문의 담당자와 영업기회 담당자는 섞지 않는다.
   - PC의 공통 판정을 operational overlay에서도 재사용한다. 모바일 전면 개편은 이번 범위가 아니다.

2. **금액 저장 정합성**
   - 견적·수주 입력은 읽기 전용, 예상금액만 일반 편집한다.
   - 견적 스냅샷은 서버 조회값/견적 버전을 우선 사용하고 로컬 편집 패치를 견적 정본으로 사용하지 않는다.
   - 예상금액 저장 payload의 `won_amount`는 항상 null. 이미 수주금액이 있는 건도 그 값을 수정 요청에 섞지 않는다.
   - 저장 전 객체/로컬 캐시 금액 변경 제거. 기존 command queue의 완료 ACK 확인 후 반영한다.
   - 거절/미확정이면 기존 값 유지, 미확정 요청이 있으면 새 중복 요청 차단.
   - 0원 저장 지원. 종료 건 편집 차단. 같은 현장 중복 클릭 차단.
   - 저장 중 다른 상세로 이동해도 완료 후 해당 화면을 강제로 다시 열지 않는다.
   - 서버의 권한·버전 충돌·견적 버전 검증은 그대로 유지한다.

3. **문의 상세의 Deal 전용 저장폼 제거**
   - 문의 기본정보·원문·응대 이력·다음처리와 연결된 영업기회 정보를 표시한다.
   - 문의에서 예상/견적/수주금액, Deal 전용 단계/활동 저장폼을 노출하지 않는다.
   - 배정·응대·다음행동·상태변경은 동일 문의 ID의 기존 문의 처리 화면으로 연결한다. 새 저장 API를 만들지 않는다.
   - 원문은 HTML escape 처리. 응대 이력 펼침은 해당 문의 상세 안에서 작동한다.

## 파일

- `crm.html`: 연결 판정, 문의 전용 상세, 예상금액 읽기/쓰기.
- `operational-overlay.js`: PC 연결 판정 중복 제거.
- `scripts/verify-detail-p1-browser.cjs`: localhost 합성 데이터 회귀검사.
- `tests/operational-mapping-hotfix.test.cjs`: 코드 모양 비교를 실제 ID 연결 판정 테스트로 대체.
- `scripts/build-local-release-candidate-manifest.cjs`, `local-release-candidate-manifest.json`: 미배포 후보 해시 갱신.

## 검증

- 전체 자동 테스트: 610개 중 **594 PASS / 0 FAIL / 16 SKIP**.
- 마지막 연결 모호성 보강 후 관련 테스트 33개 추가 재실행: 모두 PASS.
- 신규 브라우저 회귀: 동일 현장 별도 문의, 연결 ID/역방향 연결, 모호한 연결, 문의 원문 escape, 실제 문의 처리 화면 이동, 읽기 전용 금액, 저장 거절, ACK 반영, 0원, 중복 클릭, 미확정 요청 중복 방지, 저장 중 상세 이동 PASS.
- 기존 브라우저 회귀: 문의 배정·미배정 표시/카운트/서버 정본, 파이프라인 상세 활동 필터·스크롤·탭·다음 행동·즐겨찾기, 관계관리 범위/필터/상세 연결 PASS.
- PC 합성 화면 캡처를 확인했다. 실사용자 계정별 Production 저장과 전체 모바일 상세는 이번 검증에 포함하지 않았다.
- DB 관련 자동 검사는 저장소의 로컬 테스트 환경에서 실행된다. 운영 프로젝트, n8n, 잔디, 구글시트는 변경하지 않았다.

## 남은 작업

- 운영 반영 전 현재 미커밋 후보 전체 범위 확인과 Production 권한별 저장/재조회 검증 계획 필요.
- 상세 개요 축소, 연락처 보기/편집 분리, 관계관리 빠른 기록, 고객자산 복귀 맥락은 별도 P2 작업으로 남음.
- 이전 조사에서 확장관리 초기 포커스의 일회성 실패가 있었으며 이번 P1 수정으로 해결됐다고 간주하지 않는다.
- 실제 데이터의 연결 ID가 누락된 건은 같은 이름만으로 복원하지 않는다. 원본 연결 근거 확인이 필요하다.

Supabase 스킬은 서버 검증을 유지하고 ACK를 확인하는 경계를 정하는 데, frontend-design 스킬은 문의/영업기회 역할과 입력 가능한 금액을 구분하는 데 적용했다. 기존 사용자 로컬 작업은 보존했다.
