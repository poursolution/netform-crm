# 견적문의 원문·첫 연락 판정 — 기능 수정과 Claude 인수인계

작성: 2026-10-09. 대상: poursolution/netform-crm. 디자인·위치·CSS는 변경하지 않는다.

## 확인된 코드 원인

- 운영 버전 `37a7225`에서 신영프로방스 문의의 원문과 `첫 연락 기한 266일 지남` 표시를 읽기 전용으로 대조했다. 원문은 일시 머리줄 `2026/01/16 PM 05:02` 다음 줄에 `1차 통화완료`가 있다. `parse`가 줄마다 날짜를 새로 읽어 통화 후보에 날짜가 연결되지 않았고 `메모에서 찾은 통화 없음`으로 표시됐다. 일시 머리줄과 아래 기록을 연결하도록 수정했다. 일반 문장의 날짜나 상대 날짜를 통화·방문 날짜로 추정하지 않는다.
- 별개 누락도 확인했다. `memosOf`는 응대내용과 외부 응대 이력만 읽어 문의내용 필드에만 들어 있는 동일 문구는 스캔하지 않았다. 같은 줄/줄바꿈 및 원문 필드별 사례를 합성 문의로 검증했다. 실제 고객의 통화·방문 완료를 운영에서 확정한 결과는 아니다.
- 방문 약속 규칙은 방문·내방·실측만 읽고 현장 미팅을 놓쳤다.
- `InquiryV4.ext`는 첫 응대 값이 없으면 메모 근거보다 먼저 신규 첫 연락 기한을 계산했다.
- `InquiryV4`는 연락처 보완을 별도 상태로 분리한다. `ExecWording.firstBefore`는 담당·종결·전환·첫 응대 값만 확인하며 연락처 보완을 제외하지 않는다. `brief-b.js`는 별도 문의 범위에서 첫 응대 값을 확인한다. 사용자 관찰 29/52/54건은 동일 조건·동일 시점의 ID 목록 대사 전까지 현재 확정 건수로 사용하지 않는다.

## 준비한 기능 수정 — 운영 미반영

- 원문 필드(message/detail.inquiry/content/raw.문의내용)와 특이사항에서 통화·약속 후보가 있는 내용만 읽는다. 응대 메모와 중복되는 후보는 키로 중복 제거한다. 읽기만으로 완료·담당·상태·후속 업무를 저장하지 않는다.
- 미팅 약속과 다음주 요일 문구를 인식한다. 상대 날짜는 실제 방문일이나 현재 새 업무의 기한으로 자동 확정하지 않는다. 취소 예정과 통화 완료 예정·부정은 완료 후보에서 제외한다.
- 같은 글자 수로 메모를 고쳐도 분석 캐시가 갱신된다. 기존 후보 키와 과거 판단 기록을 보존한다.
- 담당이 지정됐고 첫 응대가 없지만 통화 후보 또는 날짜가 지난 약속 근거가 있는 문의는 기존 `④ 과거 기록 정리` 묶음에서 확인하도록 정렬한다. 이미 등록된 다음 할 일 날짜·앞으로의 고객 회의/회신 기한이 있으면 기존 우선순위를 유지한다. 날짜 없는 새 약속만으로 이관 기록으로 분류하지 않는다. 행/상세의 기존 안내 칸은 `이관 기록 확인 필요`, 신규 첫 연락 연체 기한은 계산하지 않는다. 담당 없는 문의는 담당 지정 우선 원칙을 유지한다.
- 진단보고서와 미팅·연계 기록이 함께 있으면 기존 첫마디 칸에서 실행 여부·보고서 제공 여부·연계 결과를 묻는다. 규칙 기반 문장이고 실제 AI 추론·완료 확인이라고 주장하지 않는다.
- `InquiryMemo.needsReview(q)`는 읽기 전용 확인 후보 판정이다. `InquiryFlow.firstConnectedAt`, 실제 최초 응대·성과·배정 원장은 변경하지 않는다. 담당자가 기존 확인 버튼으로 결정하는 경로를 유지한다.

## Claude에게 필요한 표시 결정

1. 현행 여섯 상태 탭 안에 이관 기록 확인 대상의 자리가 없다. **새 탭·카드·배치는 Codex가 만들지 않았다.** 이번 행 정렬/안내 수정만으로 첫 연락 탭의 분모가 통일되는 것은 아니다. 첫 연락 확인 / 연락처 보완 / 이관 기록 확인을 어떻게 표시할지 현재 디자인에서 결정해 달라.
2. 같은 ID 목록 기준으로 전체 = 배정 필요 + 실제 첫 연락 확인 대상 + 연락처 보완 + 이관 기록 확인 + 후속 대상이 연결되도록, 겹치는 보완 사유의 표시와 우선 분류를 결정해야 한다. 단순히 메모가 있다는 이유로 문의를 숨기거나 완료로 처리하면 안 된다.
3. 공사 견적 / 유상 진단·진단보고서 / 실제 협약·B2B 의도를 구분해 보일 위치가 필요하다. `협약`, `자료 요청` 키워드만으로 B2B 자동 이관하거나 진단 상담을 공사 실주로 바꾸지 않는다. 실제 목적은 담당 확인 후 기존 분류 명령으로 저장한다.
4. 원본 선택 공종과 상담에서 확인한 실제 범위·분류 보완 후보를 구별해 보일 위치를 결정해야 한다. `옥상(외벽균열)` 등의 기존 원문은 보존한다. 이름·키워드만으로 공종이나 브랜드를 덮어쓰지 않는다.
5. 기존 첫마디 칸의 `AI` 표시는 규칙 문장과 구별이 필요하다. 위치/스타일 결정을 Codex가 하지 않으므로 표시 방식만 인계한다.

## Codex 후속 조사 — 완료로 표시하지 말 것

- 동일 계정·브랜드·기간·담당 필터와 동일 시점으로 문의 목록·영업사원 관리·브리핑의 ID 집합을 비교하고, 삭제/종결/전환/B2B/미배정/연락처 보완/이관 후보의 제외 사유를 각 건에 남긴다. Claude 표시 확정 후 공통 판정을 연결한다.
- 운영 화면의 원문 줄바꿈·266일 지연·목록 첫 연락 29건/연락처 보완 112건, KPI 누적 첫 연락 52건은 읽기 전용으로 확인했다. 수정 이후 검증은 합성 자료이며, 배포 뒤 실제 후보 표시 확인은 남아 있다. 실제 방문/진단보고서/외부 연계 결과를 확인한 것은 아니다.
- 원본 공종 선택값과 변환 함수 입력을 대조한다. 진단·협약 의도를 임의 확정하거나 일괄 이관하지 않는다.
- #530은 별도 승인 대기 PR이다. 이 수정의 승인·배포와 혼동하지 않는다.

## 검증과 배포

관련 Node 및 기존 메모 브라우저 회귀 검사에 원문 통화·미팅·부정·중복·동일 길이 수정·읽기 전용·기한 미생성 사례를 추가했다. 새 SQL·RPC·권한·n8n은 없다. 화면/서버 원자료 변경 없이 검토 가능한 기능 수정으로 준비한다. 실제 배포 전 최신 master와 변경 파일을 대조하고 필수 CI를 통과해야 한다.

## 후속 연락 추가 점검 — 2026-10-09

- 운영 37a7225에서 천안두정 원문을 읽기 전용으로 확인했다. `[2026. 1. 7. 오후 5:06:44]`의 공백 있는 점 날짜가 문장 경계로 쪼개졌고, `보내주신다`를 우리 발송으로 바꾸는 규칙과 앞줄의 `시간이 맞으면` 조건을 놓치는 문제가 있었다.
- 약속 후보에 actor / recipient / modality / condition을 메모리에서만 계산한다. 고객 발송·우리 발송·주체 미확인을 구분하며, 확인 전 문장은 전달·방문 실행 여부를 묻는다. 날짜 파서 수정으로 과거 약속 판단 키가 바뀌지 않도록 기존 문장 기준 키를 유지한다. 완료된 약속은 질문에서 제외한다. 서버 칸·원자료·판단 이력을 추가하거나 덮어쓰지 않는다.
- 조건부·검토 중·확정 표현은 원문 근거로만 구분한다. 새 칩·배지·위치는 만들지 않았다. 별도 상태 표시가 필요하면 Claude가 위치를 정한 뒤 연결한다.
- 목록 오른쪽은 이미 접수일 복사를 경고하지만, 가운데 마지막 연락 요약은 별도 계산이었다. 같은 원래 날짜에 대한 연결 확정 문구를 `연결일 확인 필요`로 통일한다. 이후 별도로 확인된 연락 이력까지 숨기지는 않는다.
- 번호 저장 자체는 InquiryCommand의 phone 필드만 저장한다. 기존 코드도 항상 후속 연락으로 이동시키지 않았으므로 안내와 저장 성공 문구를 바로잡았다. 합성 자료로 미배정·첫 연락·이관 기록 확인·확인된 후속 상태 재계산을 검증했다. 실제 고객 번호를 바꾼 것은 아니다.
- 호매실경남 원문은 `1501동 3~4라인 ...`이었다. 세대수 매핑 오류가 아니라 요약 정규식이 동 번호를 동 개수로 바꾸는 오류였다. `개동`이라는 개수 단위가 있는 경우에만 동 개수로 요약한다. `1501동`·`1501세대` 원문을 수정하지 않는다.
- 기능 수정 파일: inquiry-memo.js, inquiry-v4.js, inquiry-workbench.js. crm.html은 변경 파일의 캐시 키만 갱신. 관련 Node 17개 및 메모·견적문의 v4 브라우저 검사 2종을 합성 자료로 확인한다. PR #531에 포함하며 아직 운영 반영은 별도다.
