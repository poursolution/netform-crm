# `crm_bundle()` 보안 검토

검토일: 2026-09-05  
상태: **운영 미적용. 로컬 분석·SQL 작성·모의 테스트만 완료.**

검증 판정: **로컬 보안 회귀검사는 통과했지만 운영 적용 준비는 미통과.** 운영 함수/ACL,
n8n JWT 역할, 배포본 호출 경로와 확장 번들의 역할별 계약을 확인하기 전에는 실행하지 않는다.

## 결론

현재 확인 기록에 따르면 `public.crm_bundle()`은 인자 없는 `STABLE SECURITY DEFINER`
함수이며, 함수 내부 호출자 검증 없이 users/deals/inquiries/brands/leads/dups를 한 번에
반환한다. PUBLIC·anon·authenticated가 실행할 수 있으면 Supabase REST RPC를 통해 RLS와
무관하게 전체 번들을 받을 가능성이 있다. 이는 브라우저에 공개해도 되는 reader가 아니다.

즉시 완화안은 `crm_read_bundle()`에서 `auth.uid()`와 활성 CRM 사용자를 연결하고 역할별로
응답을 제한한 뒤, 원본 함수의 PUBLIC/anon/authenticated 실행권한을 회수하는 것이다.
장기안은 원본 전체 번들을 만든 후 JSON을 자르는 방식을 없애고, 안정적인 담당자 ID를
조건으로 각 테이블에서 허용 행과 열만 직접 조회하는 scoped reader/RLS 구조다.

## 노출 가능 데이터

운영에서 확인했다는 함수 설명과 프론트 소비 코드를 기준으로 다음 범주가 포함될 수 있다.

- 사용자: 이름, 이메일, 역할, 활성 상태, Auth UUID
- 영업기회·문의: 고객/현장 식별정보, 연락처, 주소, 담당자, 금액, 단계, 상담 및 활동 이력
- 파생 정보: 브랜드·리드 집계, 중복 후보와 중복 판단 메모
- 운영에서 번들에 추가한 경우: 첨부 메타데이터, 캠페인, 담당자 평가/관리 코멘트,
  고객지원, ASQ 미러, 확장영업 및 관계성과 데이터

실제 열 목록과 현재 함수 본문을 이번 로컬 검토에서 운영 DB에 재조회하지 않았으므로,
위 목록을 완전한 개인정보 인벤토리로 간주하면 안 된다.

## 호출자 전수 확인 결과

저장소 전체에서 `crm_bundle`, REST RPC 경로, `crm-api`, `CRM_API`를 검색했다.

- 현재 `netform-crm/crm.html`과 `mobile.html`은 공용 `crm-read.js`를 통해
  `/rest/v1/rpc/crm_read_bundle`을 호출한다.
- 현재 프론트 코드에서 `/rpc/crm_bundle` 직접 호출은 발견되지 않았다.
- 여러 SQL 마이그레이션이 `pg_get_functiondef('public.crm_bundle()')`로 원본 함수 본문을
  수정하며, 일부 서버 통합 SQL은 내부에서 원본 함수를 호출한다. 이는 배포 시 순서와
  함수 정의 재검토가 필요하다는 뜻이다.
- README와 배포 문서에는 기존 `crm-api`/`crm-write` n8n 경로 및 번들 확장 계약이 다수
  남아 있다. 저장소 밖 구버전 배포본과 운영 n8n 워크플로 내부 자격증명은 확인하지 못했다.
- 현재 테스트는 기본 키(deals/inquiries/dups/users/brands/leads) 호환성만 보장한다.
  rep 투영은 attachments/campaigns/customerSupportActions/asq_projects/expansion_pool 같은
  확장 키를 의도적으로 버리므로, 해당 기능을 rep에게 제공해야 한다면 기능 회귀가 발생한다.

## 권한을 바로 회수할 때의 영향

| 호출자 | 예상 영향 |
|---|---|
| 현재 로컬 PC/모바일 | 새 reader 설치 및 사이트 배포가 함께 되면 정상; SQL만 먼저 적용하면 현재 배포 상태에 따라 조회 실패 가능 |
| `service_role` JWT를 쓰는 n8n/서버 | 보강 SQL이 명시적으로 실행권한을 유지하므로 원본 호출 가능 |
| anon 또는 일반 사용자 JWT로 원본을 부르는 구버전 앱 | 즉시 401/403 또는 RPC 권한 오류 |
| 함수 소유자/관리자 작업 | 소유자 권한에 따라 실행 가능 |
| 이후 원본 함수를 DROP/재생성하는 마이그레이션 | PostgreSQL 기본 PUBLIC EXECUTE가 다시 생길 수 있어 재감사 필요 |

운영 적용 전에는 n8n `crm-api` 실행 한 건의 JWT 역할이 실제 `service_role`인지 확인하고,
배포 중인 모든 PC/모바일 URL에서 `/rpc/crm_bundle` 호출이 없는지 네트워크 로그로 확인해야 한다.

## 두 설계 비교

| 항목 | 원본 차단 + JSON 투영 reader | 테이블별 scoped reader/RLS |
|---|---|---|
| 긴급 노출 차단 | 빠름 | 스키마·정책 검토가 먼저 필요 |
| 기존 응답 호환성 | 높음 | 명시적 응답 계약 재구성이 필요 |
| 최소권한 | 함수 반환 후 필터라 과도기 수준 | SQL 실행 단계부터 행·열 제한 가능 |
| 성능 | 매 요청 전체 번들 생성 | 담당자 조건·페이지네이션 최적화 가능 |
| 미래 키 추가 시 누출 | rep는 허용 키 투영으로 방어, 전체조회 역할은 그대로 | 명시적 열/뷰 계약으로 통제 가능 |
| 식별자 안정성 | 현재 담당자 이름 비교라 이름 변경·동명이인 위험 | `assignee_user_id`/Auth UUID FK 사용 가능 |

권고는 2단계다. 먼저 보강된 `20260905_crm_direct_read.sql`로 공개 실행 경로를 닫고,
그 다음 실제 원본 함수와 테이블 스키마를 기준으로 ID 기반 scoped reader를 별도
마이그레이션으로 만든다. 스키마를 모르는 상태에서 두 번째 SQL을 추측해 작성하는 것은
안전하지 않다.

단, 첫 단계도 현재 상태 그대로 운영 승인하면 안 된다. rep가 사용해야 하는 확장 키를
먼저 확정하고 각 키의 담당자 범위 투영을 추가하거나, 누락이 의도된 제한임을 제품 정책으로
승인해야 한다.

## 작성된 마이그레이션의 안전장치

- 트랜잭션 안에서만 변경하며, 원본 함수 누락 또는 SECURITY DEFINER 속성 변경 시 중단
- 새 reader는 빈 `search_path`, `auth.uid()`, 활성 사용자, 허용 역할을 확인
- rep 응답은 명시된 키만 재구성하여 미래의 번들 키가 자동 노출되지 않음
- service_role 원본 실행권한을 명시적으로 부여한 뒤 PUBLIC/anon/authenticated 권한 회수
- `has_function_privilege` 사후조건이 하나라도 어긋나면 전체 트랜잭션 롤백
- PUBLIC은 실제 역할이 아닌 pseudo-role이므로 ACL의 `grantee=0`을 검사하고,
  실제 anon/authenticated/service_role은 `has_function_privilege`로 유효권한을 검사
- 테이블 데이터, 쓰기 함수, 사용자 계정, n8n 상태는 변경하지 않음

## 운영 적용 전 중단 지점

다음은 사용자 명시 승인 전 실행 금지다.

1. 운영 DB에서 원본 함수 본문·소유자·ACL·의존 객체를 다시 덤프한다.
2. 운영 n8n과 모든 배포본의 실제 호출 JWT 역할 및 RPC URL을 확인한다.
3. 스테이징 복제본에서 익명/미등록/비활성/각 역할 계정을 시험한다.
4. 관리자 결과의 키·건수와 기존 서버 결과를 비교하고 rep 교차노출을 검사한다.
5. 실제 실행될 SQL diff, 영향받는 호출자, 복구 절차를 사용자에게 제시한다.
6. 명시 승인을 받은 뒤에만 운영 트랜잭션을 실행한다.

현재 단계에서는 위 항목을 실행하거나 운영 Supabase, n8n, 배포 사이트를 변경하지 않았다.
