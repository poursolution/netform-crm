# 문의 방문·견적 사실 저장 — 로컬 후보

2026-10-11 작성. 운영 DB에 설치하거나 활성화하지 않았다. 기존 PC 입력의 기능 배선이며 화면·배치·CSS를 바꾸지 않는다. 모바일 견적 v3의 계산·적산·제출금액·최종화는 이 계약의 범위가 아니다.

## 해결하는 문제

기존 `crm_inquiry_command_v1`의 `visit(done)`은 열린 방문 캘린더 여러 건을 완료하며 원래 날짜를 다시 쓴다. `quote_send(sent)`는 기존 열린 다음 할 일을 전부 취소하고 7일 후 업무를 만든다. 따라서 `inquiry-flow.js`의 `protectLegacySchedule`을 제거하지 않고, 보호가 켜진 경우에만 별도의 사실 저장기로 보낸다. 새 모듈이나 서버 계약을 확인하지 못하면 이전 저장으로 우회하지 않는다.

## 로컬 구현

- `inquiry-milestone-contract.js`: 현재 계정·세션, 조회 토큰, 명령/ACK/receipt 검증.
- `pc-inquiry-milestone-save.js`: 계정/문의별 `pc_milestone` 보관, 같은 요청 번호 재시도, 부분 성공 회복, 서버 확인 뒤 투영.
- `sql/inquiry-milestone-preserve-v1-20261011.sql`: 아래 함수와 기본 비활성 설정·비공개 사건 원장. `schedule-preserve-v1-20261011.sql`, 기존 문의 흐름 원장·두 연락 결과 SQL을 선행한다.
- 기존 PC 문의의 `visit`·`quote_send` 입력만 연결한다. 실제 발송 명령이나 외부 알림은 보내지 않는다.

| 함수 | 입력·출력 |
| --- | --- |
| `crm_inquiry_milestone_context_v1` | `inquiry_id` → 현재 담당/작성자, 저장 가능 여부, 현재 문의 상태, 사실·일정 토큰, 열린 업무/옛 방문 캘린더 수 |
| `crm_inquiry_milestone_save_v1` | `inquiry_id`, 보관된 `request_id`, `expected_token`, `kind`, 실제 입력 값 → 사건·감사 ID, 저장 사실, 원장 상태, 변경 뒤 토큰 |
| `crm_inquiry_milestone_receipt_v1` | 동일 문의·요청 번호 → `found`와 확정 ACK. 미발견은 저장 성공이 아니다. |

계약명은 `crm.inquiry-milestone.v1`이다. `kind`는 `visit_planned`, `visit_done`, `quote_draft`, `quote_sent`이다. 방문은 날짜와 선택한 시각, 견적은 금액(원)과 날짜를 쓴다. 날짜만 확인한 사실은 사건에 `precision: day`와 시각 미입력을 보존한다. 기존 timestamp 조회에 필요한 투영은 한국시간 해당일 00:00이며 실제 고객 연결 시각으로 쓰지 않는다.

방문 완료와 견적 발송의 사실·문의 상태는 서버에서 저장한다. 최초 응대 시각/연락 횟수, `qualified_at`, 영업건·실적·계약은 바꾸지 않는다. ACK의 `promoted`는 `false`이고 `cancelled_action_ids`, `completed_action_ids`, `changed_calendar_ids`는 모두 빈 배열이어야 한다.

## 일정 보존과 부분 성공

- 이미 열린 업무가 있는 방문 완료·견적 발송 기록은 기존 일정의 ID·원래 날짜·상태를 그대로 둔다. 자동 완료·취소와 자동 D+7 업무 생성은 하지 않는다. 기존 안내 문구로 후속 일정·전환이 별도임을 알린다.
- 방문 예정, 날짜가 있는 견적 초안은 열린 업무·옛 방문/후속 캘린더·원장 없는 평면 일정 날짜가 모두 없을 때만 공통 `ScheduleContract.add`로 새 내부 계획을 만든다. 고객과 합의한 약속으로 추정하지 않는다.
- 예정 입력에 기존 일정이 있으면 현재 폼에 특정 일정·변경 사유를 고르는 계약이 없으므로 쓰기 전에 차단한다. 새 UI를 만들거나 임의로 완료/변경하지 않는다.
- 새 일정 ACK의 정확한 요청·업무 ID를 사실 저장 RPC에 연결한다. 서버는 현재 동일 업무와 공통 일정 사건을 재검증한다. 일정은 저장됐지만 사실 저장이 실패하면 그 사실을 기존 오류 영역에 알리고 같은 ID로 나머지만 확인한다.
- 사실 ACK가 유실되면 같은 명령의 receipt를 읽는다. 입력이 바뀌었거나 계정/세션·다른 업무가 바뀌면 새 UUID로 덮어쓰지 않는다. 저장소 실패는 첫 쓰기 전에 차단한다.
- 자정이 지나도 이미 보관된 요청과 기존 일정의 원래 날짜를 유지한다. 일정만 저장된 경우에는 정확한 공통 일정 사건으로 그 원래 계획을 확인한 뒤 사실 저장을 마무리한다. 새 입력의 과거 예정일은 계속 거절한다.
- 같은 문서에서 로그아웃/재로그인한 과거 요청은 재개하지 않는다. 새로고침 후 동일 계정의 보관분은 서버 권한·담당·대상을 다시 확인하고 원 명령/토큰/UUID를 유지한 채 문서 식별자만 안전하게 재결합한다. 일정 부분은 공통 `ScheduleContract.resume`을 사용한다.
- 조회는 공통 일정 함수의 20건 페이지를 모두 검증한 후 투영한다. 목록 UI는 기존 공용 페이지 방식을 그대로 쓴다.

## 견적 원장 범위와 미지원

첫 견적 금액은 기존 `inquiry_quote_versions`에 저장한다. 동일 금액의 미발송 초안을 발송 사실로 확인하면 같은 버전을 쓴다. 이전 발송 버전은 변경하지 않는다. 미발송 초안의 수신자·방법·파일·변경 사유 키를 생략하면 원값을 보존한다. 명시 null/빈 문자열로 지우는 작업은 현재 폼의 승인된 입력이 없어 거절한다.

다음은 완료하지 않았다.

- 기존 일정의 변경·완료: 정확한 대상 ID와 변경/완료 근거를 선택하는 계약 필요.
- 금액 수정·발송 완료 견적의 재발송/새 버전: 변경 사유와 대상 버전의 명시 연결 필요. 현재 금액/날짜만 있는 폼에서는 새 일정도 만들기 전에 차단한다.
- 사실 저장 후 자동 영업건 전환: 별도 전환 권한·멱등성·확정 ACK 검증 연결 필요. 이번 저장 성공은 파이프라인 등록 성공이 아니다.
- 견적 v3의 서버 계산·PDF/제출본 최종화: Claude 담당 별도 계약이며 이 파일로 대체하지 않는다.
- 운영 설치·활성화: 별도 승인 및 운영 검증 전까지 기존 진입 보호를 유지한다.

## 검증

`tests/inquiry-milestone-sql.test.cjs`는 실제 신규 SQL과 기존 일정·문의 SQL을 내장 PostgreSQL의 합성 데이터에서 실행한다. 권한·비활성 기본값·동일 요청 재시도·원래 일정 보존·초안 메타데이터 생략 보존·명시 null 거절·계정/토큰/협약 제한을 검사한다.

`tests/pc-inquiry-milestone.test.cjs`는 실제 공통 클라이언트와 합성 RPC를 사용한다. ACK 지연/유실, 재진입 원문, 부분 성공, 중복 클릭, 저장소 실패, 계정/세션 변경, 연락·전환 사실을 섞은 잘못된 ACK, 20건을 넘는 기존 업무 보존을 검사한다. 합성 검사 통과는 운영 설치 완료를 뜻하지 않는다.
